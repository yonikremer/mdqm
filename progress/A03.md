## Summary

Partition metadata and the EXPLAIN pruning proof moved into `src/mdqm/adapters/postgresql_plan.py`,
which is pure (no connection, no clock) and testable without a server:

* `parse_partitions()` reads the `pg_partitioned_table` / `pg_get_partkeydef` / `pg_inherits` rows and
  returns one `Partitioning` per table: strategy, key, granularity, and one bound per partition with
  the range as UTC datetimes (plus `pg_class.reltuples` per partition). `PARTITIONS_SQL` moved with it.
  `PostgresAdapter.extract_partitions()` now only runs the query and delegates.
* `parse_plan()` parses `EXPLAIN (FORMAT JSON)` (never `ANALYZE`) into `PgPlan`: relations, indexes,
  parameter markers (`$0`), and `Subplans Removed`. `parse_plan()` returns `None` for anything that is
  not a plan, so garbage can never read as "zero partitions scanned".
* `pruning_verdict(summary, partitioning, scope)` turns a `PlanSummary` plus the spec's window into
  `PROVEN` / `UNPROVEN` / `UNKNOWN`, and it is falsifiable: `expected` lists the declared partitions
  the window spans, `named` the ones the plan named, `unexpected`/`missing` their difference, and
  `reason` is one sentence. `PROVEN` only on an exact set match. `stamp(summary)` writes the verdict
  back into `PlanSummary.pruning_proof`.
* `PostgresAdapter.explain()` now delegates to `parse_plan` and counts the *fragment's own tables*:
  partitions the plan named over the partitions of those tables (before, `partitions_total` was every
  partition in the database, which under-counted pruning on a server with several partitioned tables).
* `probe()` claims `partition_metadata` only after a real `extract_partitions()` call succeeded;
  a `NotSupported` or a driver error is reported as unsupported with the reason.
* `mdqm.planner.partitions.gate_plan()` (C08's module, additive) applies `max_partitions_scanned`
  to `PlanSummary.partitions_scanned` and refuses with `PARTITION_SCAN_ALL`. `errors.partition_scan_all`
  gained an optional `scanned=` so that message states the measured counts instead of claiming the
  key is unfiltered.

## Decisions

* The verdict lives on the adapter side, but it takes the window the *planner* intends
  (`mdqm.planner.partitions.Range`), because only the spec knows it. The adapter's `explain()` still
  leaves `pruning_proof=UNKNOWN`: it can produce counts, not a promise.
* `LIST` and `HASH` partitioning get `UNKNOWN`, not `UNPROVEN`: a time window does not determine
  which hash partition must be read, so any set we "expected" would be invented. C08 already rates
  hash access `ESTIMATE_UNPROVEN`; this keeps the two consistent.
* A window that spans no declared partition (both sets empty) is `PROVEN`: the plan did exactly
  what the metadata demanded. The falsification is still visible — both lists are empty and the
  reason says the plan named exactly the 0 partitions the window spans.
* `probe()` now performs one catalog read. It costs one query at probe time and buys a capability
  claim that cannot be false.
* Helper moves: `split_names` / `row_estimate` moved to `postgresql_plan.py` (public, since the
  catalog reader in `postgresql.py` uses them too) rather than being duplicated. `postgresql.py`
  imports them, so the dependency stays one-way.

## Plan issues

* TASKS.md says "`WHERE start_time >= now()-30d` reports <= 2 of 12+ partitions `proven`". A
  `now()`-based test proves nothing here: the machine clock is past the loaded window, so `now()`
  prunes every partition away (`Subplans Removed: 14`, no relation named). The test anchors on
  `2026-01-01T00:00Z` instead and says why. The canned `usage_events_runtime_bound_unpruned.json`
  keeps the `now()` shape so the parser is tested on it.
* Acceptance 3 names `PARTITION_SCAN_ALL` for "the plan scanned too many partitions". That code is
  documented as "nothing filters the key". It is true for the case that matters (a filter on the
  wrong column) and the builder now states the measured counts, but a future task may want a
  distinct code for "the plan disagreed with the metadata".
