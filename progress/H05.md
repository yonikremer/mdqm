## Summary

`src/mdqm/context/pack.py` builds the Context Pack: given a free-text question and the search index
of H04, it returns the measures, value maps, approved joins, tables and approved example specs that
matter, rendered as one compact block (`ContextPack.text`) plus the same content structured
(`items`, `omitted`). Ranking is relevance-first (how many of the question's content words found a
fact), then kind, then join usage, then bm25, then ref — all pure sorting, no clock, no randomness,
so the same question over the same semantic `version_hash` is byte-identical. The budget defaults to
1,500 tokens and is a hard ceiling measured on the rendered text with the existing C16 estimator
(`mdqm.results.summary.estimate_tokens`): the pack is shrunk from the lowest ranked fact until it
fits, and every dropped or capped fact is listed in `omitted` with `reason: budget|limit`. A
question whose words match nothing returns an empty pack (no text, no tokens), which is what a
`UserPromptSubmit` hook needs on a prompt about the weather. `budget_for_context()` scales the
budget with a probed model context window (1.5% of it, clamped to 400..4000).

## Decisions

- **Per-word search instead of one ANDed query.** H04's `search` ANDs every word, so one unknown
  word in a real Hebrew question ("הממוצעת") would return nothing. Each content word is searched on
  its own (`log_empty=False`, so a non-data prompt writes no `empty_searches` row) and a fact's
  relevance is how many question words found it. Words in a bilingual stopword list (`STOPWORDS`)
  are never searched, so "how"/"much"/"של" cannot manufacture relevance; the empty pack for
  "what is the weather" therefore comes from the data, not from a score threshold guess.
- **Approved joins are also derived from the tables the pack names.** A question about credit limits
  reaches `crm.customers`; the approved join to `billing.usage_events` is exactly the fact a weak
  agent cannot invent, and its own name never appears in the question. Only joins with a named end
  are added, so an irrelevant prompt still gets nothing. Joins are capped at 4 (usage order),
  examples at 3, tables at 6; caps are reported with `reason: limit`.
- **Column hits are folded into their parent table line** ("columns credit_limit, status") instead
  of being rendered as separate lines: the measure line already carries the source column, and a
  separate line would spend budget on a fact the agent has just been told.
- **No `catalogs` input.** A table the layer has no semantics for is still rendered, honestly, as
  `no approved semantics yet` plus the columns that matched; pulling the whole probed catalog in
  would cost budget for facts (types, comments) the pack's examples do not need.
- **Budget clamp range** is its own (`MIN_PACK_BUDGET=400`, `MAX_PACK_BUDGET=4000`) rather than the
  result-summary range (512..25000): a 25,000-token "context pack" is not a context pack. The
  clamp is reported in `budget_clamped`.
- **The delay of a late row is rendered as `max lag 6h`** (`_span`) because a raw `timedelta`
  prints as `6:00:00`, which a weak model reads worse.

## Plan issues

- **H04 cannot label a value map.** `IndexError`'s `labels` accepts `table:`, `measure:` and
  `column:` refs only (`_refs`), so a deployment cannot attach the *field's* Hebrew name to a value
  map. Consequence: the Hebrew question "מסגרת אשראי לפי סטטוס" reaches the measure but not the
  `customer_status` value map unless it also names a Hebrew value ("פעיל"). The pack tests use such
  a question. Fixing it is an H04 change (`_refs` + a `value:<name>` label bucket); it is worth
  doing before M02, because M02's acceptance is "a Hebrew question and an English question about
  credit limits return the same tables and measure".
- `TASKS.md` gives H05 no place to declare where approved example specs live. This module takes
  them as an argument (`Sequence[ApprovedExample]`, the same list H04's `build` indexes), so the
  caller must pass the same list to both; a shared loader for them does not exist yet.
