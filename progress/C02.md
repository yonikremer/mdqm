## Summary

`src/mdqm/sql/exec_ts.py` rewrites every non-deterministic SQL time function to an absolute
literal derived from **one injected `exec_ts`**, and does the same for Elasticsearch date math.
Nothing in the module reads a clock or touches I/O.

- `resolve_exec_ts(mode, clock=..., stored=...)` implements the two modes of DESIGN section 13:
  `frozen` (stored value of a past run) and `relative` (injected clock, read exactly once).
- `rewrite_sql(sql, dialect=..., exec_ts=..., session_time_zone="UTC")` returns `RewriteResult`
  (rewritten SQL + `Replacement(original, replaced_with, position)` for audit).
  Node-level detection covers the dialect-neutral `CurrentTimestamp`/`CurrentDate`/
  `Localtimestamp`/`Systimestamp`/`UtcTimestamp`/`CurrentTimestampLTZ` nodes plus a per-dialect
  name set for spellings sqlglot keeps as `Anonymous` (postgres, duckdb, oracle, tsql, mysql).
- Interval arithmetic is folded into a single literal: `now() - interval '7 days'`,
  `SYSDATE - 7`, `SYSDATE - 1 / 24`, `SYSDATE - INTERVAL '6' HOUR`,
  `DATEADD(unit, n, now)`, `DATE_SUB(now, INTERVAL n UNIT)`. Calendar units (month/year) are
  applied on the wall clock, elapsed units on the instant, so a 24h step over a DST change is
  still 24h. Wrappers that are not now-like (`TRUNC`, `ADD_MONTHS`, `EOMONTH`, `DATE_TRUNC`)
  keep their meaning; only the value inside them is replaced.
- Literals are `CAST('...' AS TIMESTAMP|DATE)` / `DATETIME2` (tsql) / `DATETIME` (mysql),
  rendered in the source's session time zone; `GETUTCDATE()`/`UTC_TIMESTAMP()` stay in UTC.
- `rewrite_es_date_math` / `rewrite_es_query` turn `now-7d/d` into an absolute `...Z` instant,
  with ES's ordering (arithmetic first, rounding last) and its `/d`, `/w`, `/M`, `/y` floors
  applied in the range's `time_zone`; only date-math range bounds are touched.
- `tests/data/golden/exec_ts_{postgres,oracle,tsql}.sql` hold every corpus statement rewritten
  with one fixed `exec_ts`, for review.

## Decisions

1. **Dialect set.** `postgres`, `duckdb`, `oracle`, `tsql`, `mysql` are supported; any other
   sqlglot dialect raises `ValueError` listing the supported ones instead of guessing which
   names are clocks there. MySQL is included because a same-named *user function* (`getdate()`
   in PostgreSQL) must never be rewritten, so detection has to be per dialect. PostgreSQL
   `getdate(u)` is therefore left alone, and a test pins that.
2. **`Replacement.original` is sqlglot's rendering**, not the exact source spelling, because the
   parser drops the spelling (`now()` becomes `CURRENT_TIMESTAMP`, `interval '30 days'` becomes
   `INTERVAL '30 DAYS'`). The audit trail stays truthful about the expression; only its
   spelling is normalised.
3. **`Replacement.position` may be `None`.** sqlglot records token offsets only for function
   calls; bare keywords (`CURRENT_DATE`, Oracle `SYSDATE`, T-SQL `CURRENT_TIMESTAMP`) have none.
   A text search of the source was implemented, then removed: with two identical functions in
   one statement it can attach the second replacement to the first occurrence, and a wrong
   offset is worse than a missing one. Documented on the model and covered by a test.
4. **`position` is `None` for Elasticsearch**, because a dict has no character offsets.
5. **Render-until-stable (max 4 passes).** sqlglot's generator is not always a fixed point on the
   first pass (T-SQL `EOMONTH` grows a `CAST` on the second), which would make "rewriting twice
   is a no-op" false for a reason outside this module. Normalising the text to a fixed point
   makes idempotence structural.
6. **Output literals are `CAST('literal' AS type)`** rather than a typed literal such as
   `TIMESTAMP '...'`, because sqlglot renders Oracle typed literals as `TO_TIMESTAMP(...,
   'YYYY-MM-DD HH24:MI:SS.FF6')`; the `CAST` form is one shape for every dialect, valid
   everywhere, and round-trips stably.
7. **`_Timestamps` need an error, not a sentinel:** naive input, unknown time zone, unsupported
   dialect and multi-statement input all raise `ValueError` with the fix in the message.

## Not verified

- **The rewritten SQL was never executed against a real engine.** No container runtime exists in
  this environment, so Postgres/Oracle/SQL Server integration could not run; every statement is
  verified by sqlglot parse + render only. In particular these remain unproven at the server:
  that `CAST('...' AS TIMESTAMP)` compares correctly with an Oracle `DATE` column, and that a
  `DATETIME2` literal matches T-SQL `SYSDATETIME()` precision.
- Elasticsearch date math is verified against the documented semantics, not against a live ES
  node (same container limitation).
