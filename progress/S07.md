## Summary
Adds stage D7 (`src/mdqm/pipeline/stages/joins.py`): join candidates measured from the catalog *and* the values. One
bounded `GROUP BY` per candidate key column reads its distinct values with row counts; every cross-table pair is then
compared under each applicable conversion (identity, zero pad, numeric, case fold, prefix strip), and the conversion that
actually matches wins. A candidate carries the containment ratio both ways, the Jaccard overlap, unmatched distinct keys
and unmatched rows (the orphans, named), a name-similarity score, a cardinality, and an `on` template that is a real
`ApprovedJoin` entry. Proposals go through `ReviewQueue` (`section="approved_joins"`, kind `JOIN`); the stage writes no
`curated/` and no `generated/` section. Against the D02 world it proposes crm.cust_id <-> billing.accounts.client_no
with `LPAD(..., 10, '0')` and 1.0/1.0 containment, crm.cust_id <-> erp.cust_no with identity and 1.0/1.0, and reports the
planted orphan keys on billing.usage_events (2 distinct keys, 20 rows) without hiding them.
## Decisions
- **Thresholds are a conjunction, not a score.** A pair is proposed only when Jaccard >= 0.5, the larger containment
  >= 0.95, and the distinct-size ratio <= 10. Containment alone would propose erp's 1/2/3 `status_code` against
  `cust_id` (fully contained); the size ratio is what rejects it. Name similarity only orders and scores.
- **Families are measured from values, not declared types.** `cust_id` (integer) and `client_no` (VARCHAR padded digits)
  are both "digits"; a text key is comparable to a digits key only when it is a constant prefix plus digits.
- **No `generated/` output.** An unknown top-level key breaks `semantic.loader`, and a join is a human gate, so the only
  durable output is the review queue (plus the `StageReport` counters). `auto_approvable` marks DESIGN 10's auto case
  (declared FK + total containment) but the stage still submits it as a pending proposal rather than approving itself.
- **Heavy stage, same gate as D5.** `heavy = True`, refuses outside a `QuietWindow` unless forced, and holds one
  `ctx.access(source)` slot per read.
- **Conversion SQL is rendered per dialect through sqlglot** (`VARCHAR` -> `TEXT` on DuckDB, `VARCHAR2` on Oracle;
  numeric casts are `DECIMAL(38,0)` because sqlglot maps `BIGINT` to a 32-bit `INT` on Oracle and a padded text key can
  hold more digits). Prefix stripping uses `SUBSTR`, which T-SQL lacks; the clause names its dialect in the evidence.
- **`inputs_hash` includes `exec_ts.date()`**, like D5: values change nightly, so a nightly pass re-measures while two
  passes on one day skip.

## Not verified
- **No live database.** There is no container runtime on this machine, so every acceptance item is proven against the
  D02 world in F05's DuckDB-backed `FakeAdapter`, which runs the real generated SQL. The stage has not been run against
  PostgreSQL/Oracle/SQL Server: the *rendered statements* are checked by unit tests and by sqlglot, not executed there.
- Dialect-specific conversion SQL (`VARCHAR2`, `DECIMAL(38,0)`, `SUBSTR`, `LPAD` on T-SQL) is asserted as text only.
- The `GROUP BY ... LIMIT cap+1` read costs one aggregate scan per candidate key column on a large source; that cost is
  bounded by the column selection and the cap, but no measurement on real data was made (no replica, no Docker).
