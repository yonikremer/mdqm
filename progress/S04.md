## Summary

Stage D5 profiling, as one object that plugs into the S01 framework (`heavy = True`, `inputs_hash`,
`run`, `write_generated`); no second framework, no new dependency.

- **Statistics answer first.** A new injectable port `OptimizerStatistics.column_stats(table)` carries
  the source's own optimizer statistics in a neutral form (`ColumnStat`). `parse_pg_stats` maps real
  `pg_stats` rows (`null_frac`, `n_distinct`, `most_common_vals`/`most_common_freqs`,
  `histogram_bounds`) into it, including PostgreSQL's negative `n_distinct` = fraction-of-rows
  convention, and takes bounds from the MCVs when a low-cardinality column has no histogram.
  `StaticStatistics` is the dict-backed implementation (what a probe result or an adapter becomes).
- **A bounded sample second.** `sample_query` renders the fetch with sqlglot from a
  catalog-validated identifier: `LIMIT` (→ `FETCH FIRST` on Oracle, `SELECT TOP` on SQL Server) by
  default, and a seeded `TABLESAMPLE` (`RESERVOIR` on DuckDB, `SYSTEM` on Postgres) only when the
  probe positively reported the `sampling` capability. `Limits` caps rows, bytes and time.
- **Provenance per fact, not per table.** `distribution_provenance` covers null rate, distinct,
  bounds and top-N (one family, one decision); `value_shape_provenance` covers format and
  granularity. `ABSENT` is a first-class answer, so "nothing could measure this" is never silent.
- **Value shape.** `detect_format` (Unicode-aware character class, uniform width, zero padding,
  matching share) and `detect_granularity` (the whole 5000/1000/500/100/50/10/5/1 ladder with each
  candidate's share and a 0.99 threshold).
- One `generated/profile_<source>.yaml` fact sheet per source, with row estimate, rows sampled, the
  row cap, `sample_complete`, the sample method and seed, so D7/D8 can tell a sample from a table.

## Decisions

1. **`shape=False` is the cheap mode, and it is the literal reading of "sample only when statistics
   are absent or stale".** Value-shape facts (format, granularity) *cannot* come from any statistics
   table — only from values. So: a table whose statistics are fresh and cover every column costs
   **zero data queries** when the caller does not ask for shape, and one bounded fetch per table
   otherwise. The test `test_a_stats_only_pass_costs_no_data_query` asserts `adapter.calls == []`.
2. **Statistics with no `analyzed_at` are stale.** `pg_stats` carries no timestamp; only
   `pg_stat_user_tables.last_analyze` does. Freshness that cannot be proven is not freshness, so the
   conservative path (sample) wins. Staleness is computed against the injected `exec_ts`, never the
   wall clock.
3. **Granularity threshold 0.99, not 1.0.** One dirty row must not collapse a real 5000 to 1. The
   full candidate ladder ships with every granularity, so D8 still sees that 5000 fits 0.3% of the
   billing column — which is the acceptance criterion, not a rounding artefact.
4. **An unknown row estimate is read as "over the cap"** (`sample_complete: false`) and reported as
   an applied fix. Assuming a table is small is how a bounded fetch turns into a scan.
5. **`inputs_hash` includes the date of `exec_ts`.** A profile is a fact about a day: a nightly pass
   must re-measure (data grew), two passes on one day must not. Nothing in the hash reads data, so
   it stays a pure function of declared inputs as the `Stage` protocol demands.
6. **Each fact family is atomic.** A column's null rate, distinct, bounds and top values always come
   from the same origin, so a fact sheet can never mix a statistics null rate with a sampled
   distinct count and look self-consistent while being neither.
7. **A failed or timed-out fetch loses one table, not the pass.** `NotSupported`/`TimeoutError` from
   the bounded read become a line in `skipped` and leave that table's columns `ABSENT`; anything
   else propagates so the runner records `FAILED` (never swallowed).
8. **Endpoint and data-stream kinds are skipped in words**, not profiled as if they were tables.

  Podman, WSL2 store broken), so there is no PostgreSQL. `pg_class.reltuples`/`pg_stats` were **not**

  and the port is proven with `StaticStatistics`. A real adapter that queries those views is the
  next task's work; nothing here claims a measured `reltuples`.
- **`TABLESAMPLE SYSTEM` on a real PostgreSQL.** Rendered and asserted as SQL text (percent,
  `REPEATABLE`), never executed. Its behaviour on a small table (a page-based percentage can return
  zero rows) is why `sample_query` keeps tables under 50x the sample size on plain `LIMIT`; that
  guard is a reasoned choice, not a measured one.
- **Oracle/SQL Server row-bound output** (`FETCH FIRST`/`SELECT TOP`) is asserted as rendered text
  from sqlglot, not executed against those engines.
- `usage_events` (5001 rows) is profiled in the world tests but only its datetime/text shapes are
  exercised; no acceptance criterion depends on it.
