## Summary

`query` is a real pipeline body (`src/mdqm/server/tools/query.py`), in the order the task names:
**lint** (`mdqm.linter.lint_spec` / `lint_sql`) -> **compile** (`mdqm.compiler.compile_spec`, one
fragment, one source) -> **plan** (the static estimate from `planner/partitions.py`, then the
source's own `EXPLAIN` + A03's `PlanSummary` gated by `gate_plan`) -> **cache**
(`FragmentCache`, keyed by the compiled SQL + semantic version) -> **execute** through
`Governor.execute` (never an adapter) -> **summarise** (`results.summary.summarise`) ->
**history** (`HistoryStore.record`) and **audit** (`AuditLog`, ok and refused alike).

The answer is one model, `QueryAnswer`: `status` (`ok` / `dry_run` / `error` / `not_implemented`),
`summary`, `sample`, `result_handle`, `rows_total`, `cache_hit`, `freshness` (one row per source with
its own `fetched_at` and cache status), `plan` (partitions scanned/total, `partitions_if_fixed`, the
pruning verdict and the planner's notes) and `applied_fixes` (every repair, lint then compile).
Every refusal is an `ErrorResponse` with `code` + `problem` + `fix`, and every refusal is audited.

Also changed: `src/mdqm/server/tools/__init__.py` now re-exports the body from the new module instead
of holding the stub, and `docs/tool-schemas.json` is regenerated (the signature grew the emergency
`sql` / `source` arguments; `dry_run` and `fresh` already live on the spec).

## Decisions

1. **The cache unit is the fragment, not a partition window.** The task pointed at
   `cache/segments.py`; C17's `FragmentCache` (in `executor/cache.py`) is the piece that already
   applies C12's freshness rule to one whole fragment, and its own docstring says it exists so the
   project does not grow a second, disagreeing cache rule. `SegmentCache` needs a partition-aligned
   `Range` per table plus a fetcher, and a table with no partitioned time column has no window to
   align -- using it here would have meant inventing one. The observable contract the task asks for
   is met exactly: an identical repeat makes **zero** adapter calls and reports the first call's
   `fetched_at` per source.
2. **`EXPLAIN` runs only when the source is really about to be asked**, i.e. after a cache miss and
   after `dry_run` has returned. A cache hit therefore costs no source call at all, which is what
   "a repeated query makes zero source calls" means; the static partition estimate is still reported
   on a hit.
3. **A spec is re-parsed before it is linted.** The MCP boundary validates the wire model (structure
   only); `parse_spec` also runs the cross-field rules, so a spec that arrives as JSON gets the same
   `INVALID_SPEC` answer it would get from a dict. Cheap, and it keeps one validation path.
4. **Refusals are `BLOCKED` audit rows** whatever their code (`record_refusal` is the store's own API
   for that). A request the pipeline refused is a blocked attempt, and the code it was given is in
   the row.
5. **The tool tolerates a server with no pipeline**: it answers `not_implemented` with `problem` and
   `fix`, like the lookup tools, because a wiring bug is not the agent's to fix.

## Deviations

* **No context pack on errors / success.** TASKS.md describes "a compact context pack on every error
  and (budget permitting) on success". A pack is built from `mdqm.context.pack` over a `ContextIndex`
  (an FTS index of the semantic layer) that the server builds at startup; wiring that index into this
  tool belongs to the context lane's surface (`/context`), and this task owns only `query.py` and its
  test. What the agent gets instead is the specific, actionable part: the exact `fix`, the plan, the
  freshness and the handle. Follow-up worth a task of its own: pass an optional `ContextPack` builder
  into `QueryServices` and attach the pack to errors.
* **The raw-SQL path skips the `EXPLAIN` gate.** A statement does not declare which tables it reads,
  so there is no partitioning to gate against; it still goes through the guard (first lint rule), the
  linter's repairs and the governor, and a refusal is audited. The spec path -- the one the agent is
  told to use -- has the full gate.
* **`query` gained `sql` and `source` arguments**, which changes the advertised tool schema. The
  generated `docs/tool-schemas.json` is regenerated in this commit; `spec` is still the documented
  path and carries `dry_run` / `fresh`.

## Dependencies

None added. The tool reuses `duckdb` (already required) only through the injected `FragmentCache`.

## Not verified

* **Startup wiring in `mdqm serve`.** `configure_query_services(...)` is the seam, and it is not
  called from `server/app.py` yet: building a `Governor`, a `FragmentCache` and the stores from
  settings is the server lane's job (and `app.py` is not in this task's `owns` list). Until then a
  served ``mdqm serve`` answers `not_implemented`, exactly as the five tools did before M03. Both
  test files build `QueryServices` explicitly, which is what proves the pipeline itself.
* **`usage_events` pruning is proved on the server's counters**, not by reading the plan XML:
  `pg_stat_statements` shows the refused query contributing nothing and the bounded one incrementing
  (a positive control in the same test), and the refusal itself is an audited row. The pruning
  *verdict* comes from A03's `gate_plan` over the adapter's `PlanSummary`, which A03 already proved
  against real plan text.
* **Multi-source specs** are out of scope (M04 owns the federated join). `query` compiles exactly one
  fragment for one source; a spec naming an approved join still compiles to the single-source
  fragment the compiler produces.
