## Summary

`tests/eval/questions.yaml` holds 15 analyst questions (8 Hebrew, 7 English, every question with both
phrasings on one record, so the two languages cannot drift onto different answers), each with the
canonical spec an agent should send, a difficulty-tag set, and the expected answer as data.
`tests/unit/test_eval_questions.py` proves the fixture: shape (15/8/7, closed tag vocabulary, required
tag counts, exactly one of `spec`/`statement`), every `spec` validates through `mdqm.spec.parse_spec`
and the answer's columns are the names that spec produces, and every answer is reproduced by **two
independent derivations**, neither of which runs the code under test:

1. a hand-written `oracle_sql` executed on DuckDB over the three storage forms loaded straight from the
   world's frozen dataclasses (the normalisation `(x + 2500) // 5000 * 5000` and `limit_k * 10` is
   spelled out in SQL, not imported);
2. a plain-Python recomputation from `World.expected` and the world's rows (no DuckDB, no spec, no
   semantic layer), for all 13 rows answers.

Coverage of the MVP situations: average credit limit by status from all three sources (crm identity,
billing `ROUND(x/5000)*5000` with NULLs, erp `x*10` with duplicate rows), a late-arriving-rows
`new_since` question, a total-since question, a known-as-of-T question, a partition-filter refusal
(`PARTITION_SCAN_ALL`, checked structurally: the spec really carries no window and no filter on
`start_time`), and a blocked DELETE (`WRITE_BLOCKED`, cross-checked with `mdqm.sql.guard`).
Required counts: needs_conversion 4, needs_value_map 5, needs_insertion_time 3.

## Decisions

1. **`oracle_sql` per question instead of executing the spec.** The compiler/executor does not exist on
   `main` yet, so "execute the expected spec" is impossible without inventing the thing under test.
   The fixture freezes what the spec *means* as hand-written SQL, and E02 (harness) runs the real path
   and compares against the same stored answers. The test docstring says this plainly.
2. **Golden-file workflow, with a second opinion.** The answers were produced from the oracle SQL, so
   that pairing alone would only be a regression guard. The pure-Python recomputation in
   `independent_answers()` is the real check: it disagrees with the SQL if either is wrong (both were
   exercised with mutations - a changed count and a truncated float both fail).
3. **Absolute windows everywhere** (`time.from`/`to`) instead of `last: '3mo'`. Resolving a trailing
   window needs an `exec_ts` and the time planner (C07, another lane); absolute bounds keep the
   fixture deterministic today. E02 can add `last:`-style questions on top once the planner lands.
4. **A `usage_units` measure is assumed and documented** in the fixture's `semantic_assumptions`:
   `examples/semantic_example.yaml` declares only `credit_limit_r5000`, and a spec can aggregate only
   measures, so counting usage events needs one. It is canonical/identity in every source; the test
   asserts `units` is never NULL, which is what makes `count(usage_units)` a row count.
5. **Canonical value vocabulary** is the example's (`active`/`churned`/`suspended`, Hebrew labels
   `פעיל`/`עזב`/`מושעה`). The fixture repeats the source-code mapping (`A`/`Active`/`1`, ...) in its own
   SQL and Python instead of importing the semantic layer, on purpose.
6. **`world.sha256` pins the data.** If D02's generator changes, the hash changes and the answers must
   be regenerated deliberately rather than drifting.
7. **Float comparison at relative 1e-15** (declared in the YAML). Money averages come from integer sums
   below 2^53, so two correct implementations agree to a few ULPs; a truncated digit still fails.
8. Answers live in the same YAML record as both phrasings, so "he and en share one ground truth" is
   structural, not a promise: there is exactly one `answer` per question id.

## Plan issues

- **The spec cannot express three question shapes an analyst really asks**, so this set omits them:
  latest-revision-per-key (`billing.accounts_hist`, mutability class `mutable_critical`), a difference
  between two time columns (`insertion_time - start_time > 1h`, a natural "how late do rows arrive"
  question), and "rows with no match on the other side" (orphan `client_no`s). Each needs a spec
  concept (distinct-on / computed value / anti-join) that C03 does not have; they are worth a task.
- **`examples/semantic_example.yaml` declares no measure for usage events**, so counting events is not
  expressible against the reference layer. Either the example gains `usage_units`/`event_count`, or a
  future task defines how a plain `count(*)` is spelled.
- The task text says "8 Hebrew and 7 English"; with both phrasings on every question, `language` is the
  primary language only. The test pins that mix so a new question keeps it.
