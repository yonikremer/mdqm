## Summary
A real `SourceAdapter` implementation over in-process DuckDB (`src/mdqm/testing/fake_adapter.py`), so
every other lane can test execution, planning, caching and the governor with NO container runtime.
Rows live in a real DuckDB database (`CREATE TABLE ... AS SELECT` from Arrow), the fragment SQL is
actually executed there, and `execute` streams real `pyarrow.RecordBatch` values through a lazy
`FakeStream`. It passes `run_conformance` (F04) both with every optional capability declared and with
none. `Limits` are enforced by the adapter itself: `max_rows` is exact (the last batch is sliced, not
batch-rounded), `max_bytes` stops the scan early, and `timeout_s` is honoured *while waiting* (the
simulated latency re-checks a monotonic deadline in 5 ms slices and raises `FakeAdapterTimeout`
the moment it passes), never checked after completion. `calls` records each fragment's SQL in order.
Optional capabilities are declared, never assumed: pass `partitioning`/`explain_enabled`/
`query_history`/`mutability` and `probe()` reports them and the methods work; omit them and the same
methods raise `NotSupported` with the matching capability name, which the probe then reports.
`explain()` is derived from the declared partition bounds, so the explain gate's control flow is
testable. `FakeAdapter.for_world(world)` loads one generated `World` as five tables
(`customers_crm`, `accounts`, `usage_events`, `accounts_hist`, `customers_erp`); tests prove all three
storage forms return correct rows and that the planted NULLs, orphan keys and duplicate erp rows
survive the load.

## Decisions
1. **No `mdqm.adapters` entry point for the fake (the F04 question).** The fake is registered
   explicitly (`registry.register("fake", FakeAdapter)`) or built directly; a test proves that path.
   Rationale: `AdapterRegistry.discover()` is what a real deployment runs, so an entry point would let
   a YAML typo (`adapter: fake`) silently answer from fabricated data in production — the exact silent
   failure principle 10 forbids. A plugin entry point should name a *source*, and the fake is not one.
2. **A bare `FakeAdapter()` seeds one generic one-row table** (`mdqm_fake_probe(one INTEGER)`) so it is
   still a valid source for `run_conformance` (which requires a non-empty catalog). Real rows arrive via
   `tables=` / `for_world`. No organisation facts are baked in.
3. **`kind = "fake"`** and `config.adapter` must match when a `SourceConfig` is passed, so the same
   mismatch the registry checks also fails loudly at direct construction.
4. **`Partitioning` has no table field**, so the adapter keeps `{table_name: Partitioning}` and
   `extract_partitions()` returns the values; `explain()` uses the same mapping to pick a target table
   (`fragment.tables` first, else the single declared table).
5. **Failure/latency injection is constructor-level** (`latency_s`, `fail_with`, `fail_after_calls`) so a
   test can build a source that is slow or broken without a monkeypatch.
6. DuckDB is opened `:memory:` with `SET memory_limit` and, when `spill_dir=` is given, `SET
   temp_directory` — DuckDB's own spilling, no extension, no `INSTALL`, no network.

## Deviations
- `table_from_rows` takes `Sequence[Any]` (dataclass instances) instead of a precise protocol, because
  `dataclasses.asdict` needs a `DataclassInstance` that typeshed does not export publicly; the
  docstring says what it accepts. No behaviour difference.
- `explain()` decides "pruned or not" by whether the partition key name appears in the fragment SQL.
  That is a deliberate fake (`# shortcut:` comment in the code), not a predicate parser: it drives the
  explain gate's control flow and never claims a real pruning decision.
