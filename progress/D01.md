## Summary
Shipped the dev environment for the whole project: a five-service `docker-compose.yml` where every
service sits behind a profile so a task starts only what it needs (`pg` ~1 GB is what the MVP uses),
`scripts/dev.py` as the stdlib, Windows-safe wrapper (`up` uses `docker compose up --wait`, so a green
exit means healthy; `down` removes the volumes), `scripts/wait_for.py` for a TCP port or HTTP URL,
`.env.example` with throwaway dev credentials only, `docs/dev-env.md` (install, profiles vs tasks, RAM,
port map, troubleshooting), the Postgres seed (`docker/pg/init/01-init.sh`: databases `crm`/`billing`/`erp`,
read-only role `mdqm_ro`, `pg_stat_statements` in all three) and the D04 mock API image
(`docker/api.Dockerfile`, wired to `python -m mdqm.testing.mock_api --serve`, nothing rewritten).
`tests/unit/test_dev_env.py` asserts what can be asserted without a runtime: profiles, pinned tags,
loopback-only non-default ports, a healthcheck per service, every `${VAR}` present in `.env.example`,
throwaway-only credentials, no Windows-specific paths, `.env` git-ignored, and the graceful
missing-docker path.

## Decisions
1. **No credential in any shipped file, not even a compose default.** Every password is
   `${MDQM_*:?...}`; a missing `.env` makes Compose fail loudly instead of starting a server with a
   blank password. `dev.py env` creates `.env` from `.env.example` once (git-ignored), so the documented
   `python scripts/dev.py up pg` still works on a fresh clone with zero extra steps.
2. **`status: partial`, not `done`.** The acceptance items that need a container runtime (`config -q`,
   `up pg` healthy + exit 0, `down` removing volumes, the seed, `pg_stat_statements`, `mdqm_ro`) are
   unverified by definition here. Writing `done` would claim a container was started; none was.
3. **Pinned tags chosen from the task's own wording, no `latest` anywhere:** `postgres:16`,
   `gvenzl/oracle-free:23-slim-faststart`, `mcr.microsoft.com/mssql/server:2022-CU14-ubuntu-22.04`,
   `docker.elastic.co/elasticsearch/elasticsearch:8.15.3`, and `mdqm/mock-api:dev` (built here). The
   oracle and mssql tags were confirmed to exist by a web lookup, not by a pull.
4. **Host ports** `55432 / 51521 / 51433 / 59200 / 58000`, all on `127.0.0.1`, all overridable from
   `.env` (`MDQM_*_PORT`) — non-default so a local engine is never shadowed.
5. **The mssql healthcheck probes the socket, not the server.** The 2022 image ships no `mssql-tools`,
   so `bash -c 'exec 3<>/dev/tcp/127.0.0.1/1433'` is the honest readiness signal available in-image.
6. **The Postgres read-only password is injected, not written.** The seed is a `sh` script that passes
   `$MDQM_RO_PASSWORD` to `psql -v` and lets the SQL use `:'ro_password'`, so no file in the repo holds
   a password. `mdqm_ro` also gets `default_transaction_read_only = on` and `SELECT` on future tables
   (`ALTER DEFAULT PRIVILEGES`), which is layer one of the three read-only layers.
7. **`pg_stat_statements` is created in all three databases** (not only `crm`), because the mining stage
   reads it through whichever connection it opened.
8. **Elasticsearch keeps its 1 GB heap and no `bootstrap.memory_lock`**: memory locking fails on some
   Docker Desktop/WSL2 setups and would turn a working dev stack into a restart loop.

## Plan issues
- D01's test command (`docker compose ... config -q`) is unrunnable in any environment without a
  container runtime, and the task's own note ("if Docker is not available ... run only `config -q`")
  assumes `config -q` works without Docker. It does not: `docker compose` *is* the Docker CLI plugin.
  A machine-checkable proxy (`tests/unit/test_dev_env.py`) is what this branch offers instead; a future
  task could add `compose-spec` schema validation in Python if that matters.
- `docker-compose.yml` and `.env.example` are listed in the repo layout in `AGENTS.md` but were absent, so
  every acceptance criterion that assumed them was untestable until now.
- Nothing in the backlog owns the Postgres seed SQL or the mock API image; if another task later moves
  the seed (e.g. D02/D03 loading the synthetic world), it should extend `docker/pg/init/01-init.sh`
  rather than adding a second init file with overlapping grants.
