## Summary
`src/mdqm/semantic/values.py` adds the value-map resolver on top of C04's frozen `ValueMap`; no
parallel model, no edit to `models.py`. `resolve_value(map, label, field=..., column=...)` normalises
any spelling (NFKC, niqqud, geresh/gershayim, case, whitespace, via `semantic.text.normalize_label`),
then unions three kinds of hit: canonical spellings, both-language synonyms and the source codes of
the named column (all columns when none is named). One hit resolves; several hits return
AMBIGUOUS_VALUE with the matched values; no hit returns UNKNOWN_VALUE with every valid canonical
value plus `did_you_mean` from difflib. `reverse_value` resolves first (so any spelling works) and
returns `SourceLiteral(column, literal)` for each source, sorted by column, with `int` for a
lossless integer code and `str` otherwise. Errors come from the existing `mdqm.errors` builders.
Table-driven tests cover Hebrew (with niqqud), English, `' Active '`, `'a'`, `'Hold'`, `1`;
hypothesis proves normalisation is idempotent, a canonical value resolves to itself, a resolved
label's literals all map back through `canonical_for`, and no resolution invents a value.

## Decisions
- Source codes are folded through the same normaliser as labels (`hold` finds billing's `Hold`
  and the CRM's `A`). A layer that spells two different values `A` and `a` therefore reports
  AMBIGUOUS instead of guessing which case the user meant; the map is the thing to fix.
- Ambiguity is decided on the union of canonical/synonym/code hits. The loader cannot catch the
  canonical-vs-synonym overlap (`_consistent` only compares synonyms with synonyms), so `open` in
  `canonical: [active, open]` + `synonyms: {active: [open]}` resolves as AMBIGUOUS here.
- `column=` scopes code matching only, never synonym matching: a language label means the same
  thing in every source.
- Reverse type: `ValueMap` stores codes as text (`1` arrives as `"1"`), so the type is
  reconstructed here for a *lossless* integer spelling only (no sign `+`, no leading zeros, <= 18
  digits). `"01"` stays text because it is a zero-padded identifier; converting it would silently
  filter the wrong rows. If a source ever needs a numeric-looking string code, the map is where the
  exception must be stated, not this heuristic — flagged in the module docstring.
- `AMBIGUOUS` candidates are the matched values (that is the choice to make); `UNKNOWN` candidates
  are all canonical values (that is the reference). Both are exact tuples, not suggestions.
- A canonical value with no binding in the named column is valid with `literals == ()`: the value
  exists, that source does not store it, and the compiler decides what to push down.
- `did_you_mean` is attached with `ErrorResponse.model_copy` because `unknown_value` takes only
  `valid_values`; no second message template was written and no code was added to `errors.py`.
- `label` accepts `int` so a JSON integer filter value (`{"value": 1}` on the ERP) resolves; the
  error text stringifies it.
