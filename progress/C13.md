## Summary
Added `src/mdqm/cache/singleflight.py`: `SingleFlight.do(key, fn)` coalesces concurrent callers of one
key into a single `asyncio` task behind `asyncio.shield`, so every caller receives the *same* result
object (hence one `fetched_at`) and callers never own the work. The key is dropped on success and on
failure, so a failed call is broadcast to its waiters and the next call retries instead of replaying the
error. A re-entrant call (fn asking for its own key) raises `RuntimeError` instead of deadlocking; a blank
key raises `ValueError` instead of coalescing unrelated callers. `flight_key(source, query, params,
exec_ts)` builds the identity: SHA-256 over a canonical JSON envelope, `exec_ts` normalised to UTC, params
canonicalised so dict insertion order cannot change a key, unknown parameter types refused rather than
falling back to an address-bearing `repr`.

## Decisions
- **Query text is hashed verbatim** (case and whitespace matter). A missed coalesce costs one source call;
  a wrong coalesce hands one caller another caller's answer. SQL normalisation belongs to the AST
  fingerprint (task C10), not to the coalescing key.
- **`flight_key` lives in `cache/singleflight.py`, not `sql/fingerprint.py`**, because `sql/fingerprint.py`
  is in C10's `owns` list (AST mining) and creating it here would collide with that lane. When C10 lands,
  its AST fingerprint is the natural input for `flight_key`'s `query` argument; nothing in C13 has to move.
- **`exec_ts` is part of the identity, and only as an instant**: the same instant written in two zones is one
  key, a different instant is another key (the answer can differ). Naive datetimes are refused, matching
  `freshness.py`'s rule that time is timezone-aware UTC internally.
- **Decimal, float and int stay distinct keys** (`Decimal("1")` ≠ `1`), and `True` ≠ `1`. Erring towards a
  missed coalesce rather than a wrong one.
- **Callers share one result object rather than one copy per caller.** That is what makes "same `fetched_at`"
  true, and it is why the result must be treated as immutable by callers.
- **Failures are not cached and are not stored**: the key is removed in the task's done callback, which also
  retrieves the exception so an abandoned failure cannot surface as "Task exception was never retrieved".
- **No counters in the helper.** Cohort size is observable from the shared result's provenance (`fetched_at`
  and the audit trail), and stats that nobody consumes are dead weight; the governor (C15) owns reporting.
- One `SingleFlight` per event loop (tasks are loop-bound), documented in the module docstring.

## Deviations
- Smallest possible edit to `src/mdqm/cache/__init__.py` (re-export `SingleFlight`, `flight_key`,
  `KEY_VERSION`, and update the one-line docstring) so `from mdqm.cache import ...` matches how
  `freshness` is exported. That file is not in C13's `owns` list.
- `tests/unit/test_singleflight.py` carries `pytestmark = pytest.mark.enable_socket`. On Windows every
  asyncio event loop's self-pipe is a `socket.socketpair()`, which pytest-socket blocks in `tests/unit`, so
  *any* async unit test needs it (same reason `test_server_skeleton.py` has it). No test here opens a
  network connection: the only "source" is the in-process DuckDB fake.
- The hang guard helper is generic (`within(awaitable) -> T`). Typed as `-> object` first, which made every
  test body an attribute access on `object`; a linter pointed it out, so the coroutine's type now flows
  through to the assertions.

## Dependencies
none (stdlib only: `asyncio`, `hashlib`, `json`, `functools.partial`).

## Not verified
- Real database concurrency (Postgres/Oracle/SQL Server) and driver-level cancellation: no container runtime
  on this machine. The "one source call for N callers" acceptance is proven against
  `testing/fake_adapter.py`, which is the project's definition of a real adapter and records its calls.
- Cancelling a *server* task through to a driver cancel API: that is the governor's contract (C15); C13 only
  guarantees the flight itself survives a cancelled waiter.
- Cross-process stability of the key is pinned by a frozen golden digest rather than a subprocess run (a
  `hash()`/`id()`/dict-order dependence would make that literal fail on every run).
