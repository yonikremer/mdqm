## Summary

`src/mdqm/adapters/sqlserver.py` is a pooled, streaming, read-only `SourceAdapter` for one SQL
Server database, built on `mssql-python` (the D06 extra, imported lazily so `tests/unit` needs no
driver): catalog from `sys.*`, `extract_partitions()` from `sys.partition_functions` +
`sys.partition_range_values` + `sys.partition_schemes` + `sys.destination_data_spaces`,
`execute()` returning `ArrowStream` of `pyarrow.RecordBatch` under `max_rows`/`max_bytes`, a
deadline watchdog that calls `cursor.cancel()`, `explain()` from `SET SHOWPLAN_XML ON`,
`mine_queries()` from Query Store and `mutability_stats()` from `sys.dm_db_stats_properties`.
Registered as the `sqlserver` entry point in `mdqm.adapters`.

## The plan-XML question (AGENTS.md section 9) — answered empirically

The flagged unknown was "SQL Server plan XML for partition counting is unverified". Measured on
SQL Server 2022 `16.0.4135.4`:

1. **An estimated plan (`SET SHOWPLAN_XML ON`) does carry the pruned range**, as a seek predicate on
   the computed partition-id column — not as a count:
   `<StartRange ScanType="GE"><RangeColumns><ColumnReference Column="PtnId1000"/></RangeColumns>
   <RangeExpressions><ScalarOperator ScalarString="(9)"/>` and `<EndRange ... "ScalarString="(11)-(1)">`
   — i.e. partitions 9..10, so `partitions_scanned = end - start + 1 = 2`.
2. **`RunTimePartitionSummary/PartitionsAccessed/@PartitionCount` is NOT in an estimated plan**; it
   exists only in an *actual* plan (`SET STATISTICS XML ON`), which requires executing the statement.
   So it cannot be the count an `explain()` reads.
3. Both agree where they overlap — the actual plan for the same statement says
   `<PartitionsAccessed PartitionCount="2"><PartitionRange Start="9" End="10">`, and the integration
   test asserts that agreement instead of trusting the parser.
4. When the key value is a parameter (auto-parameterisation does it to `CONVERT(datetime2,@1)` too),
   that same place holds `RangePartitionNew(CONVERT(datetime2(6),[@1],126),(1),'2024-11-01'...)`
   instead of a number, so the ends are unknown before execution → `unproven`, never a guess.
5. **A `varchar` literal on a `datetime2` partition key eliminates nothing**: the estimated plan has
   no `PtnId1000` predicate at all and the actual plan reports `PartitionCount="18"` (all partitions)
   versus `2` with `CONVERT(datetime2(6), '2025-06-01', 126)`. The compiler must render a time
   literal as `datetime2`, not as a string, or every partition is scanned.

`GRANT SHOWPLAN TO [mdqm_ro]` is required for step 1: `SET SHOWPLAN_XML ON` succeeds without it and
the *statement* is then refused with `SHOWPLAN permission denied in database 'erp'`. The probe
reports `explain_plan` unsupported with that fix when the grant is missing.

## Decisions

- **Driver: `mssql-python`.** Table of findings in `docs/mssql-driver.md`; it is the only candidate
  with wheels that bundle the ODBC driver and its DLLs, which matters in an air-gapped on-prem
  network, and it is what D06 loads the world with. `pymssql`/`pyodbc` stay optional extras (not
  installed or measured here, marked "not installed" in the doc rather than pretending a measurement).
- **Deadline via `cursor.cancel()`, not `Connection.timeout`.** Measured: `cancel()` interrupts a
  running statement *and* a blocked fetch (`Operation canceled`) and the session survives;
  `Connection.timeout` also works (`Query timeout expired`) but fires on the driver's schedule, so it
  is a backstop at `timeout_s + 5 s`, never the deadline.
- **`cancel()` sets a client flag that the iteration honours.** The driver's `SQLCancel` only lands
  while an operation is in flight; a cancel that arrives between two fast batches did nothing in a
  measured 25M-row stream (the loop ran to completion). With the flag, `cancel()` is authoritative and
  the abandoned statement has still been broken server-side. A second `cancel()` stays a no-op.
- **Partition count is `sys.partition_functions.fanout`, and the bounds are built from the tuples.**
  `sys.destination_data_spaces` has one *extra* row (`ALL TO ([PRIMARY])` reserves a destination for
  the next split), so counting destinations would report 19 partitions for an 18-partition table.
  A tuple count that disagrees with `fanout` raises `NotSupported` instead of patching the list.
- **`RANGE LEFT`, non-temporal keys and non-RANGE functions raise `NotSupported`.** A `RANGE LEFT`
  tuple closes the partition on its left, so a half-open `[lower, upper)` bound would silently drop
  the rows exactly on the tuple; the planner cannot express it without losing data.
- **Bound names carry the partition number and its filegroup** (`ps_usage_events_month.9 (PRIMARY)`),
  because a partition has no name of its own in SQL Server.
- **`explain()` verdicts**: literal partition-id range → `proven` with a counted
  `partitions_scanned`; a `RangePartitionNew(...)` expression → `unproven`; a partitioned table with
  no partition predicate (a full scan, e.g. the `varchar` literal) → `unproven`; no partitioned table
  → `unknown`. `partitions_total` comes from the catalog, never from the plan.
- **`mutability_stats()` reports row counts and `modification_counter` only.** SQL Server keeps no
  per-table row insert/update/delete counters; `sys.dm_db_index_usage_stats.user_updates` counts
  index maintenance (once per index, reset by a restart), so it stays `None` — the cache's
  conservative fallback already treats unknown as mutable.
- **`mine_queries()` leaves `user=None`**: Query Store records no executor.
- **`fragment.params` is refused with a precise message.** T-SQL placeholders are positional (`?`)
  while a fragment's `params` is an unordered JSON object, and the compiler inlines literals.

  self-signed, so the dev config sets `trust_server_certificate: yes`; a production CA path is
  untested here.

  ignores it, so nothing proves its effect (no availability-group listener to test against).
- SQL Server's `datetime2(7)` boundary rendering: the parser accepts up to nine fractional digits, but
  the D06 function is `datetime2(6)` and only that was seen.

## Plan issues

- The task text says "count partitions in the plan XML". Measured, the count lives in
  `RunTimePartitionSummary/PartitionsAccessed/@PartitionCount`, which an *estimated* plan does not
  contain; the estimated plan carries a partition-id *range* instead. Anyone implementing this from
  the task text alone would look for an element that is only present after execution.
- `mdqm_ro` needs `GRANT SHOWPLAN` for `explain`. The D06 loader grants `db_datareader` and
  `VIEW DATABASE STATE` only, so a fresh `python -m mdqm.testing.loaders.sqlserver` run leaves
  `explain_plan` unsupported until an operator grants it (the probe says so, with the exact fix).
  Either D06's `grant_read_only()` should include it or this needs documenting in the deployment
  guide; I did not edit D06's file.
- `Partitioning` has no way to say "this engine prunes on a computed partition id, and the pruned
  range came from the plan rather than the partition list" — the model fits, but the planner will
  need the `explain()` verdict to be its source of truth for SQL Server, not `bounds`.
