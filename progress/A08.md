## Summary
`src/mdqm/adapters/sqlserver.py` is the SQL Server `SourceAdapter`: catalog from `sys.tables`/
`sys.columns`/`sys.key_constraints`/`sys.indexes`, **partition metadata read from the partition
function and scheme** (`sys.partition_functions`, `sys.partition_range_values`,
`sys.destination_data_spaces`) with real boundary values assembled into half-open `[lower, upper)`
bounds, a streaming `execute` with row/byte caps and a deadline watchdog that cancels the driver call,
`cancel`, and `NotSupported` with the capability names from `OPTIONAL_METHODS`. Registered through the
`mdqm.adapters` entry point.

## ANSWERED: the plan-XML question from AGENTS.md section 9
That section said "SQL Server plan XML format for partition counting is **unverified**". It is now
verified on SQL Server 2022, and the answer is *no* for counting and *yes* for evidence:

- the XML carries `StmtSimple/@StatementEstRows` and `@StatementSubTreeCost`, which the adapter reads;
- it does **not** enumerate partitions touched -- a partitioned read appears as one `IndexScan`;
- it **does** carry a `SeekPredicates` block naming the partition column, so pruning evidence can be
  derived from it. The adapter does not yet derive a verdict, so `explain()` returns
  `pruning_proof=UNKNOWN` while the four tests expect `UNPROVEN`/`PROVEN`.

That is why this row is `partial`: the surface works and is proven (14 tests), the verdict is a
deliberate, documented gap rather than a hidden one.
