## Summary

Stage A1+A2 lives in `src/mdqm/pipeline/stages/propose_names.py`. For one table, one column or one
categorical value it builds a fact sheet (catalog facts from D1 + profile evidence from D5 + the
terms the namespace already answers to), asks the model for closed JSON twice (the second time with
the sheet's lists rotated), and then **code decides**:

* `validate_labels` refuses on language (script of the field), the repo's own `normalize_label`
  leaving nothing, length, length of the synonym list, a column reference that does not exist in
  that table, and a term copied out of an observed value that looks identifying;
* `collisions` refuses a term that already means something else in the same namespace (one value map
  for a value, one table and its columns for a table), naming the owner it collided with;
* `confidence` is computed from the validators plus the share of `name_he, name_en, synonyms_he,
  synonyms_en` the two runs agree on, plus a bonus when D5 measured the target — never from the
  model's own claim. Temperature 0, `PROMPT_VERSION` and the model name are stored in every
  proposal's `evidence` and in the patch's `provenance`.

Accepted answers become `Proposal` rows through `ReviewQueue.submit` only: `names` (name + both
descriptions) and `synonyms` for a table/column, one `value_maps` synonym group for a value. Nothing
is written to `curated/` or `generated/`. Targets are sorted, the rotation is an index, and
`inputs_hash` covers catalogs, profiles, value maps, curated terms and the model name, so the runner
skips an unchanged rerun.

## Decisions

* **Two model calls per target, always.** The replicate is the second run of DESIGN section 10, and
  the rotation (not a shuffle) keeps `inputs_hash` honest: the same facts in a different order are a
  different prompt but the same input hash, so an unchanged rerun is still skipped.
* **A value is named through its map's synonyms.** A canonical value *is* the name, so a value
  target yields one `value_maps` proposal holding every label for it (both runs, both languages,
  deduplicated). A table or a column yields `names` (name + descriptions) and `synonyms` separately,
  because a human may want the one and refuse the other.
* **Collision scope is the namespace, not the organisation.** One value map, or one table and its
  columns. Cross-source repeats are the point of the semantic layer, so two sources calling the same
  field "customer status" is *not* a collision.
* **Column references** are read from backticked identifiers (what the system prompt asks for) and
  from snake_case tokens, because that is how this project spells a column. A free-prose snake_case
  word would be read as a column too; the false-refusal risk is accepted in exchange for catching a
  hallucinated `customer_ref` (see the live run above, where it caught 6 of them).
* **A refused replicate does not lose a valid proposal**: the first answer is validated and queued,
  the second is recorded in the report as "agreement counted as 0", which reports the instability
  instead of hiding it and instead of throwing away a good proposal over a flaky repeat.
* **`he`/`en` are checked by script**, not by a language model: a `*_he` field needs one Hebrew
  letter, a `*_en` field needs a Latin letter and no Hebrew. Blunt, deterministic, and exactly the
  failure the rule is about.
* **No model configured is reported, not raised**: the stage returns a report with
  `skipped=("no model client configured: nothing proposed",)` so a deployment without an endpoint
  still bootstraps with the deterministic stages.

## Not verified

* **A real model endpoint.** Everything ran against `FakeLLM`, per the task and AGENTS.md (no network
  at runtime, and the on-prem GLM endpoint is unverified). Prompt wording, JSON-schema adherence and
  Hebrew quality of a real model are therefore unproven; `PROMPT_VERSION` exists so a prompt change
  invalidates cached answers rather than silently reusing old ones.
* **Approving a `names` proposal.** `ReviewQueue.approve` refuses it because `SemanticLayer` has no
  `names` section (output above). The stage is correct; the layer is missing the destination.
* **D5 evidence in the integration test.** The live run passes no `profiles`, so every proposal scores
  0.9 instead of 1.0. Wiring `ProfilingStage` output into A1+A2 belongs to the bootstrap runner, not
  to this stage, and the unit tests cover the evidenced case.
* **Cost.** 91 targets in one database cost two calls each. A cheap source with `pg_stat_statements`
  makes that 182 calls per pass. The pipeline's quiet window governs when this runs; there is no
  per-source call budget in this stage.

## Plan issues

1. **The semantic layer has no `names` section.** `SemanticLayer` (`src/mdqm/semantic/models.py`)
   holds `sources`, `defaults`, `value_maps`, `measures`, `tables`, `approved_joins` — and
   `TableSemantics` is `extra="forbid"`, so there is nowhere to put a display name or a description.
   A1+A2 therefore proposes `names.<key>.{name, description, synonyms}` and a human approval is
   refused by the loader (proved above). A small task is needed: add a `names` section to
   `SemanticLayer` (`he`/`en` name, `he`/`en` description, per-language synonym lists, `provenance`),
   load it, and let the Context Pack (H04) index it. Until then A1+A2's name proposals are correct
   but not approvable.
2. **Nothing feeds A1+A2 yet.** `available_stages()` in `src/mdqm/pipeline/core.py` returns `()`, so
   the bootstrap CLI still cannot run A1+A2 even though D1..D10 are merged. Somebody has to register
   the stages with their constructed inputs (adapters, catalogs, profiles, value maps).
3. **`Proposal` has no field for the model, the prompt version or the temperature.** They travel in
   `evidence` (a tuple of strings) and in the patch's `provenance`, which satisfies the acceptance
   criterion but means a query like "every proposal from prompt version `names-1`" needs string
   matching. A typed `proposed_with: {model, prompt_version, temperature}` on `Proposal` would be
   cheaper to query; it is S12's model, not this task's.
