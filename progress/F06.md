## Summary
`mdqm/errors.py` is the agent-facing error taxonomy: `ErrorCode`, a closed set of 18 stable codes, and exactly one
keyword-only builder per code, each returning the existing `mdqm.models.ErrorResponse` with a concrete `fix`
that names the spec field or value to change (`"from"`, `"select"`, `"time"`, `"limit"`, `"group_by"`, `"joins"`,
`"sql"`, `"fetched_at"`). Guard codes are reused verbatim from C01 (`PARSE_ERROR`, `WRITE_BLOCKED`,
`MULTI_STATEMENT`) and are never renamed. `BUILDERS` maps code -> builder and is read-only, so a code can never
ship without a builder.
Three doors map real failures onto the taxonomy: `from_guard(guard(...))` (C01's rejection, re-sanitised),
`from_validation_error(ValidationError)` (a malformed spec, reading only the error type, the field path and the
allowed values) and `from_exception(exc)` (a `NotSupported`-shaped adapter error, a `TimeoutError`, an `OSError`
from a named source, or anything else -> a logged `INTERNAL_ERROR` carrying a correlation id). The exception text,
its `__cause__` and its `__context__` never reach the response; the operator gets them in the log, keyed by the id.
Every interpolated string passes one funnel (`_build` -> `_safe`): one line, no control characters, at most 512
characters (96 for an identifier), no credential pattern (key=value, DSN userinfo, bearer/basic, JWT, PEM private
key, AWS key id) and no stack trace. `tests/unit/test_errors.py` proves exhaustiveness, actionability and the three
no-leak claims table-driven, including the mapping from real failure modes in both directions.

## Decisions
* **The task's list plus five codes, each because a distinct fix needs a distinct code**: `INVALID_SPEC` (malformed
  spec; the prompt names it as a failure mode), `UNKNOWN_VALUE` (a label matches nothing; `AMBIGUOUS_VALUE` is the
  label matching two or more, and its fix is "pick one" while this one is "use one of these"), `RESULT_TOO_LARGE`
  (the response row cap; `COST_TOO_HIGH` is the pre-run estimate gate and per TASKS.md line 759 also the fragment
  cap, so conflating them would tell the agent the wrong thing), `NOT_SUPPORTED` (an adapter's `NotSupported`),
  `INTERNAL_ERROR`. 18 codes total, listed with the lane that raises each in the module docstring.
* **No free text in any builder.** Parameters are identifiers (table, column, value, spec field, source,
  capability), enums and numbers; there is no `sql`/`statement`/`detail`/`message` parameter and a test asserts
  that by signature. That is the structural half of "no SQL with literals from other users": there is no channel
  into which another user's statement could be poured.
* **`from_exception` never interpolates the exception.** `INTERNAL_ERROR` says what to do (retry, then report the
  id) and nothing about what happened; the id is `uuid4().hex[:16]`, so it is not derived from the failure either.
  The exception and its traceback are logged with `exc_info` plus `correlation_id`/`error_code`/`exception_type`.
* **A `ConfigError` maps to `INTERNAL_ERROR`**, not to a spec error: a server misconfiguration is not something the
  agent can fix, and its text names config files and key paths the agent must not see. Same for a code outside the
  taxonomy: `from_guard` turns a renamed code into `INTERNAL_ERROR` and logs it, so the closed set is enforced at
  runtime as well.
* **`from_validation_error` reads only `type`, `loc` and `ctx["expected"]`** - never `msg` and never `input`, which
  is where pydantic puts the offending value and where an agent can leave a pasted token. The field path is
  rendered dotted (`time.mode`, `filters.0.value`) to match the `error_path` values already in
  `examples/query_specs.json`; `root` can prefix it when a spec sits inside a larger payload.
* **`_safe` redacts rather than truncates a credential-shaped substring**, and redacts a whole string that contains
  a stack-trace marker (a caller handing over a traceback is a bug, and a safe message beats a faithful one). It is
  idempotent, which the funnel relies on because builders scrub their identifiers and `_build` scrubs the finished
  text again.
* **`did_you_mean` is computed here**, not by the caller: difflib plus substring containment ("status" ->
  "customer_status" scores below difflib's cutoff on its own), case-insensitive, at most 3 candidates.
* **`ErrorResponse` (F02) was not modified.** The taxonomy builds the existing model; there is no second error model.
  `code` stays a `str` there, so other lanes can still construct the model directly - see Plan issues.

## Not verified
* **Python 3.11 and 3.13 were not run.** The venv is 3.12.15. The module uses only 3.11-era features
  (`StrEnum`, `X | Y`, `MappingProxyType`), and `ruff`/`mypy` target 3.11, but only 3.12 has a green run.
* **No container runtime on this machine, so no integration test ran.** F06 has no service-dependent acceptance
  item: the whole task is pure functions over exceptions, specs, SQL text and identifiers, and `pytest-socket`
  blocked sockets for the whole unit run.
* **Adoption is not enforced.** Nothing stops a later lane from building `ErrorResponse(...)` directly and bypassing
  `_safe`; the guard is that every builder is in `BUILDERS` and `from_guard`/`from_exception` are the two doors.
  A validator on the model was rejected: it would have to import this module from `mdqm.models` (a cycle), and a
  rejecting validator would turn an error path into an exception. `models/` is also outside this task's `owns`.
* **`_safe` cannot tell another user's statement from a driver message.** The defence is structural (no free-text
  parameter, `from_exception` reads no text) and is tested as such; it is not a runtime guarantee for text an agent
  passes as its own identifier, which can only echo that agent's own input back to it.

## Plan issues
* C01's guard puts up to 200 characters of the sqlglot parser message into `PARSE_ERROR.problem`, which can quote
  the caller's *own* statement. Left as is (it is C01's text and it is the caller's own SQL), but any later lane
  that routes a *stored* statement - history replay, query store - into a guard message would leak another user's
  SQL through `from_guard`. Worth a line in H03/S08: never re-guard stored SQL into an agent-facing message.
* `ErrorResponse.code` is a plain `str` in `mdqm.models` (F02). A future task could accept `ErrorCode` there, which
  would make the closed set a type-level fact instead of a test-level one; it needs `mdqm.models` to import
  `mdqm.errors` (or the enum to move into `models`), which is why F06 did not do it.
* C15 (governor), C16 (summariser) and M01 (server) all need codes F06 already provides; they should import the
  builders rather than build `ErrorResponse` by hand, otherwise the wording and the scrub drift per lane.
