## Summary

`src/mdqm/semantic/measures.py` normalises a measure's per-source storage forms to the one canonical
value, with rounding that is declared rather than inherited from an engine, and with every applied
conversion reported.

- `render_normalize(measure, column, identifier, dialect)` parses the `{col}` template with sqlglot,
  rewrites `ROUND(x)` into explicit arithmetic, casts both sides of every division to an exact
  `DECIMAL(38,6)`, and renders per dialect. `HALF_UP` becomes
  `FLOOR(ABS(q) + 0.5) * SIGN(q)` and `HALF_EVEN` a `FLOOR`/`MOD` case, so PostgreSQL (half-up on
  `numeric`, half-even on `double`), Oracle and SQL Server cannot each pick their own tie rule.
- `check_normalize_template` enforces the allowlist (arithmetic, `ROUND`/`FLOOR`/`CEIL`/`CAST`):
  a subquery, an unknown function, an aggregate or a scaled `ROUND` is a load-time error naming the
  template path. Wired into `MeasureSource`, so a hand-edited YAML file fails at `load()`.
- `round_to_multiple(value, step, mode)` is the reference implementation for all five rounding
  modes, using exact integer `Fraction` arithmetic: no `round()` (half-even) and no binary float.
- `check_multiples(values, step)` reports and counts values that left the canonical grid; it never
  raises, skips NULLs and bounds its sample.
- `normalizations_for(...)` returns one `AppliedNormalization` per source column (template, mode,
  rendered SQL, `identity` flag) so a non-identity conversion appears in `applied_fixes` instead of
  happening silently.

## Decisions

- **`half_up` means ties away from zero.** That is the `decimal`/DESIGN spelling and it matches
  `testing/world.py:round_half_up`, so `-2500 -> -5000`, not `-0`. Documented in the docstring and
  pinned by negative cases; the world only generates non-negative limits, so this was a real choice.
- **Every division is cast to `DECIMAL(38,6)`.** PostgreSQL and SQL Server divide integers with
  truncation, so `2500 / 5000` is `0` and the boundary row would round to `0`, losing the exact case
  the measure exists for. The test proves the cast is load-bearing by evaluating the uncast form
  under DuckDB's `integer_division` setting rather than assuming the behaviour.
- **The SQL is generated from the sqlglot AST**, not string-concatenated, and the ROUND rewrite emits
  `FLOOR`/`ABS`/`SIGN` arithmetic instead of a bare `ROUND`, because `ROUND`'s tie rule is exactly
  the thing that differs per engine.
- **Rounding mode is mandatory where rounding happens.** A template calling `ROUND` under a measure
  with no `canonical.rounding` raises `UndeclaredRounding` instead of defaulting to half-up: a
  default here would answer correctly for one organisation and wrongly for the next.
- **A scaled `ROUND(x, n)` is rejected at load time.** It cannot express the canonical rule, so it
  fails where it is written rather than silently rounding twice.
- **The multiplicity check cannot catch an off-by-one-step error.** The world's planted erp
  exceptions are `limit_k + 500`, i.e. `*10` lands on `canonical + 5000`, which is still a multiple
  of 5000. That is a genuine limit of a grid check, so it is asserted in a test that names it, and
  the cross-source agreement test is what catches those rows. Reporting the limit beats hiding it.
- **`AppliedNormalization.identity` is populated for identity templates too**, so "nothing was
  converted here" is stated rather than left to inference.

## Not verified

- **No live PostgreSQL/Oracle/SQL Server.** There is no container runtime in this environment (no
  Docker/Desktop/Rancher/Podman), so the dialect criterion is met by asserting the rendered SQL text
  and evaluating it after transpiling back to DuckDB, not by executing on real servers. The rendered
  text for all three dialects is asserted, and `CAST` renders as `NUMBER` on Oracle and `NUMERIC` on
  T-SQL. Whether Oracle/T-SQL accept the exact `CASE`/`MOD` combination is unconfirmed; nothing here
  depends on a vendor function beyond `FLOOR`, `CEIL`, `ABS`, `SIGN`, `MOD`, `CAST`, which all four
  engines document.
- **`DECIMAL(38,6)` scale.** Six decimal places is ample for a 5000 granularity, but a template
  dividing by something that needs more scale would round at the sixth digit. No such template
  exists in the layer today; the constant is one place to change.
