## Decisions

1. **The cross-source plan is derived from the spec, never from fragment SQL.** Tables come from
   `from` + the approved joins' partners; columns from `resolve_column` / the measure's declared
   sources; keys from the approved join's own sides. Nothing is parsed out of a query text.
2. **Every step is a real compiled fragment.** The sub-spec carries only what that table answers
   (its columns, its filters, the anchor's time window), so the partition refusal, the value map,
   the measure normalisation and the guard all run exactly as in the single-source path — and the
   local aggregate applies the measure's per-source normalisation (`billing` `ROUND(x/5000)*5000`,
   `erp` `x*10`).
3. **A join is `inner` when the partner's columns reach the answer, `semi` when the partner is the
   many side and they do not, `left` otherwise.** The rule is fixed and reported per join: `inner`
   is what E01's answer means (an event with no customer cannot be reported by status), and `semi`
   is what keeps `erp`'/`billing`' duplicate-or-multiple keys from inflating an average — `crm_erp`
   is declared `one_to_many`, so a row-producing join would double-count the planted erp
   duplicates.
4. **`federated_plan` returns `None` for a single-source spec**, so the dispatch is one call in
   `_run_spec` and M03's path is provably untouched (its 11 tests and its integration tests still
   pass unchanged).
5. **A shared `FederatedExecutor` is injected through `QueryServices`.** The executor owns the
   fragment cache, so "a repeated cross-source query is free" only holds if the executor survives
   between calls; without one, the tool still answers but builds a per-call executor, reports every
   step as `uncached`, and never fakes a hit.
6. **The `group_by` on the credit question is written as the physical `status`,** because with three
   tables in scope the value-map field `customer_status` is genuinely ambiguous (the linter refuses
   it with `INVALID_SPEC` and a `fix`, which has its own test). Documented rather than special-cased.
7. **`order_by` on the federated path is limited to output columns** — that is what the local
   statement can sort by without re-reading a source — and anything else is refused with a `fix`
   naming the output columns.

## Deviations

* **The federated path does not run the source's `EXPLAIN` gate.** M03 explains one fragment and
  gates it with A03's verdict; `FederatedExecutor` has no EXPLAIN hook and this task owns neither
  `executor/` nor `query.py`'s plan stage. What a federated fragment still gets is the compiler's
  static partition plan (so an unbounded `usage_events` fragment is refused with
  `PARTITION_SCAN_ALL` and zero source calls, proved in a unit test) and C17's row/byte caps
  (`COST_TOO_HIGH` before the join, proved in a unit test). Follow-up worth a task: an
  `explain`-per-step hook in the executor.
* **`docs/DESIGN.md` is unchanged.** DESIGN has no section on the tool's cross-source dispatch
  (the behaviour is described in `TASKS.md` C17/M04 and in the new module's docstring); writing a
  new DESIGN section is a design decision this task does not own.
* **`src/mdqm/server/tools/query.py` was edited minimally** (not in `owns`): two `QueryServices`
  fields (`executor`, `spill_dir`), one `QueryAnswer` field (`quality`), and the six-line dispatch
  in `_run_spec`, plus the regenerated `docs/tool-schemas.json`. Nothing else in M03's body changed.
* **`tests/integration/test_tool_query_federated_e2e.py` is a new file** beyond `owns`: the proof
  the task requires is a real-PostgreSQL proof, and there is no other place to put it.
* **The integration layer is the curated example plus E01's two stated assumptions**
  (`usage_units`, and an approved mutability class for the three customer tables), applied to a
  copy with a recomputed `version_hash`. `examples/semantic_example.yaml` is unchanged.

## Plan issues

* **`errors.from_exception` does not classify `psycopg_pool.PoolTimeout` as `SOURCE_UNAVAILABLE`.**
  A source that is down therefore answers `INTERNAL_ERROR` with a correlation id, which the agent
  cannot act on, although the report correctly says `complete=false`. The fix belongs in
  `src/mdqm/errors.py` (+ its own test) — a duck-typed "could not get a connection" failure should
  map to `SOURCE_UNAVAILABLE` when `source` is given. Not this task's file, so it is reported, not
  patched.
* **TASKS.md M04 acceptance says "for the last 3 months"**, but the E01 answer it also demands
  describes November+December 2025. Both are covered: the absolute spec (E01's own) is the
  ground-truth comparison, and a unit test proves `last: "2mo"` from the world's anchor answers the
  same rows, i.e. the relative window is resolved by the tool and not by the caller.
* **A spec that spans sources but groups by a value-map *field* is refused as ambiguous** whenever
  more than one table in scope stores that map. That is the correct conservative answer, but it
  means a weak model asking "average credit limit by customer status" across three sources gets a
  refusal rather than an answer; a follow-up task could let the spec name the field *and* its table
  (`group_by: ["crm.customers.customer_status"]`) and compile the CASE under that alias.
