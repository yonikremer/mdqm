## Summary
Append-only, hash-chained audit log in `src/mdqm/store/audit.py`, with its table shipped as
`src/mdqm/store/migrations/0002_audit.sql` alongside H01's `0001_initial.sql` (same one-statement-per-line
convention). Each row's `hash` is the SHA-256 of a canonical JSON rendering of its own fields plus the
previous row's hash, so an edit, an insertion or a mid-chain deletion breaks verification at the first
affected id. `verify_chain()` returns the first bad link (`first_bad_id` + a plain-English `problem`).
Refusals are first-class: `record_refusal()` takes the guard's own `ErrorResponse`, so a blocked `DELETE`
is audited with the exact `WRITE_BLOCKED` code the agent saw. Retention purge removes only a whole aged
prefix and writes a checkpoint so the chain stays verifiable. CLI `mdqm audit verify` exits 0/1 and
`mdqm audit purge` applies retention.

## Decisions
- **Append-only enforced twice.** `BEFORE UPDATE`/`BEFORE DELETE` triggers in the migration abort the
  ordinary case (another lane, an ad-hoc `sqlite3` edit); the hash chain is the real guarantee, since a
  trigger can be dropped by anyone who can write the file. `purge()` drops and restores the DELETE trigger
  inside its own transaction, reading the DDL back from `sqlite_master` so the trigger text has one home.
- **The row id is inside the hash.** A deletion then leaves an id gap, which is a second, independent
  signal next to `prev_hash` linkage.
- **The head hash is mirrored into H01's `mdqm_meta`** under `audit.head_hash`. Without it, truncating the
  newest rows leaves a self-consistent chain that would verify — the mirror is what catches a removed tail.
- **The model has no payload field at all.** `AuditEntry` cannot represent SQL text, a result row or a
  request body, so no caller can leak one; a test asserts the table's column set and that extra fields are
  rejected. Every text field is length-capped, refused on whitespace/quotes/`=`/`\`, and refused outright if
  it matches a credential shape (JWT, `Bearer …`, PEM header, `AKIA…`, `password=`, `scheme://u:p@host`).
- **A refusal never echoes the offending value.** `AuditError` names the field only; quoting the value would
  write the very credential being rejected into the exception, the log, and any traceback.
- **Injected clock, one reading per write.** `ts` and the head mirror are threaded from a single clock read,
  so they cannot disagree, and tests never sleep.
- `AuditError` subclasses both `StoreError` and `ValueError`, so pydantic validators report it as a normal
  field rejection while `except StoreError` still catches it at the store boundary.
- CLI reads the DB path from `Settings().paths.metadata_db` and calls the idempotent `Store.initialize()`
  first, so `mdqm audit verify` works on a fresh or an already-migrated file.

## Not verified
- `tests/integration` and `--require-services`: not applicable, H02 has no integration acceptance item and
  SQLite is in-process. Nothing in this task needs Docker (none available in this environment).
- Concurrency across processes: `Store.writing()` serialises writers in-process and the chain is computed
  inside that transaction, but I did not test two OS processes appending simultaneously (DESIGN §14 is a
  single instance; SQLite's own `BEGIN IMMEDIATE` + busy timeout covers the cross-process case).
- A hash chain detects tampering, it does not prevent it: someone who can write the file can drop the
  triggers and rewrite every row from the edit onward. The design goal is detectability, and this is stated
  in the module docstring rather than papered over.
