## Summary

Stage D10 as code in `src/mdqm/pipeline/stages/drift.py`. `diff_snapshots` compares two
`CatalogSnapshot`s (plus optional per-table `Partitioning`, which a snapshot does not carry) and
classifies every change as breaking or non-breaking across 19 change kinds (added/removed/renamed
column, portable and native type change, nullability, index added/removed/redefined, primary key,
foreign keys, table added/removed/kind, partition strategy/key/granularity/bound added/removed).
Detection is gated on `snapshot_hash` (F02), so `captured_at`, `row_estimate` and column `ordinal`
churn returns an empty report before any comparison runs — no second comparison engine.

`semantic_index` maps every semantic YAML entry (measures, value maps, joins, table time columns,
partition keys, business keys) onto the `source.table[.column]` it reads, so a dropped column names
the measure that breaks. `DriftReport.blocked` is the set of entries an **unapproved breaking**
change makes unusable; the stage persists it in `mdqm_meta` and `blocked_references(store)` is the
read seam a linter or the server calls before answering from such an entry. Breaking changes are
filed as review-queue proposals (S12) on the affected table's `provenance`, and the admin
notification payload is stored (`read_notification`) — immediate, not the weekly digest. The baseline
does not advance while breaking changes are undecided, so the drift stays visible; once every
breaking change is approved the baseline advances and the block list empties.

## Decisions

1. **No new migration.** The baseline snapshot and its partition map are one document per source in
   `mdqm_meta` (migration 0001), so this lane adds no numbered migration and cannot collide with a
   parallel lane's numbering. One source = one row, not a table of records.
2. **No `generated/` section for drift.** The semantic loader validates the merged document and an
   unknown top-level key makes the whole layer unloadable (verified: `generated/capabilities.yaml`
   alone already makes `load()` fail on `sources.crm.version`). A breaking change is a question for
   a human, so it goes to the review queue, not into generated facts.
3. **`field=""` on the proposal, patch carries `provenance`.** With `field="provenance"` *and* a
   `provenance` patch the queue nested it twice (`tables.<key>.provenance.provenance`) and approval
   was refused by the loader; the patch is the table's map, so the field path is empty.
4. **Only `approved` unblocks.** A rejection or `never_ask` keeps the change blocking: the source
   still changed, so the entries reading the gone column are still wrong, and the queue already
   remembers nobody wants asking again.
5. **Rename needs an unambiguous pair.** Exactly one removed and one added column in a table with
   the same portable+native type, nullability and (unknown-or-equal) ordinal is `column_renamed`
   (still breaking). Two candidates degrade to `column_removed` + `column_added`; guessing would
   send a human to the wrong measure.
6. **Nullability is breaking both ways**, and a native-type re-spelling that leaves the portable
   type unchanged is reported non-breaking. Conservative means "visible", not "alarming".
7. **Dropped index: breaking only with an access guarantee** (covers a `use_by_default`/`indexed`
   time column, a partition key, or is the primary key). Any other dropped index is reported
   non-breaking: it is a cost fact, and crying breaking for it trains the reader to ignore reports.
8. **`inputs_hash` reads the catalog.** A catalog extraction is a metadata read, and the catalog is
   this stage's real input; hashing anything else would let a changed catalog be skipped as
   "unchanged input". The per-pass memo is cleared at the start of every `inputs_hash` for the same
   reason — a snapshot cached across passes would describe a catalog that no longer exists.
9. **An unloadable layer does not stop the diff.** D10 then classifies without a YAML mapping and
   says so in `skipped`; refusing to diff would hide the drift as well. Blocking still works for
   table-level refs; column-level blocking needs a layer, which is the honest limit.

## Not verified

- **No live database.** This machine has no container runtime, so drift was proven against
  generated `CatalogSnapshot`s and `Partitioning` values, and through `Store`/`ReviewQueue` on
  `tmp_path` — not against a real PostgreSQL catalog changing under a real `extract_catalog()`.
  Nothing in this module is dialect-aware, so the gap is the extraction, not the diff.
- **No real administrator reached.** The notification is a stored payload plus
  `read_notification()`; SMTP/pager delivery is a separate task (DESIGN section 10 mentions internal
  SMTP with a static-page fallback), so "an admin was notified" means "the payload is durably
  recorded", not "mail was sent".
- **No CLI verb added.** `mdqm bootstrap run --stage D10` works only once the wiring task registers
  the stage object in `available_stages()`; D10's constructor needs the adapter's `extract`, which
  is outside this task's `owns`.
