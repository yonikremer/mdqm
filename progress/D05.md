## Summary

`src/mdqm/testing/loaders/oracle.py` loads the billing form of the synthetic world into Oracle Free
23ai (Thin mode, no Oracle client) with the same rows as D03's PostgreSQL loader: `accounts` (raw,
unrounded `credit_limit`, zero-padded `client_no VARCHAR2(10)`), `accounts_hist`, `status_lookup`
(Hebrew + English), and both usage tables. `usage_events` is
`PARTITION BY RANGE (start_time) INTERVAL (NUMTOYMINTERVAL(1,'MONTH'))`; the loader creates exactly
one sentinel partition (`P_INIT`, `< 2000-01-01`) and Oracle derives one monthly partition per month
the data touches. `start_time` carries a **LOCAL** index (a global index would answer the query
without touching a partition and hide pruning from the plan); `insertion_time` has no index, exactly
as in D03. `usage_by_load` is interval partitioned on `insertion_time` so the event-time versus
ingestion-time choice exists in Oracle too.

The loader also creates the owner schema (`MDQM_BILLING`) and makes `MDQM_RO` what its name
promises: every role it holds is revoked (the compose image ships `DB_DEVELOPER_ROLE`, which can
`CREATE TABLE` - verified directly), `CREATE SESSION` is granted back, and only `SELECT` on the
loaded tables plus `SELECT` on `V$SQL` follows. Idempotency is drop/recreate (`DROP TABLE ... PURGE`),
so a second run leaves the same rows, indexes and partition boundaries (the `SYS_P<n>` names are
dictionary values and legitimately differ per run).

CLI: `python -m mdqm.testing.loaders.oracle [--small] [--host] [--port] [--service] [--months]`.

## Decisions

* **`TIMESTAMP(6)` holding naive UTC, not `TIMESTAMP WITH TIME ZONE`.** Interval partitioning is not
  supported on a `WITH TIME ZONE` column: Oracle answers `ORA-03001: unimplemented feature`
  (reproduced first, before writing the loader). DESIGN keeps one UTC `exec_ts`, so the loader stores
  naive UTC (`to_stored_timestamp`) and refuses a naive input instead of guessing.
* **LOCAL index.** Oracle's default index for a partitioned table is global; measured here: with the
  global index `EXPLAIN PLAN` shows only `INDEX RANGE SCAN` and no partition operation at all, so
  PSTART/PSTOP stay empty. `CREATE INDEX ... LOCAL` produces `PARTITION RANGE ITERATOR` with the
  numeric range the acceptance criterion asks for.
* **Owner schema is `MDQM_BILLING`, created by the loader**, logging in with the same throwaway dev
  password as `SYS` (`MDQM_ORACLE_PASSWORD`): the image only creates `APP_USER`/`MDQM_RO`, and one
  fewer credential in `.env` is one fewer thing to keep in sync. `target.owner_password` documents it.
* **Role revocation is part of the read-only guarantee**, not an assumption about the image. Without
  it `MDQM_RO` could `CREATE TABLE` (`DB_DEVELOPER_ROLE`); the test fails if a role ever comes back.
* **`dbms_stats.gather_table_stats` runs after the load.** Without statistics the optimizer does not
  prune, and the PSTART/PSTOP assertion would be vacuous.
* **Oracle 23ai numbers missing DML privileges `ORA-41900`**, DDL/`TRUNCATE`/`DROP` `ORA-01031`, and a
  write inside `SET TRANSACTION READ ONLY` `ORA-01456`. The test accepts the family and asserts the
  message is a privilege error; the transcript below records the exact texts.
* **`accounts_hash` (HASH partitioning) is not loaded**: no D05 acceptance item needs it, and D03 keeps
  that shape for the closed-set argument. Easy to add later by copying its DDL.
* **The dotenv helpers are duplicated** (`read_dotenv`, `find_dotenv`) instead of imported from the
  PostgreSQL loader: `psycopg` is an optional extra, and importing it from an Oracle-only module would
  make the `oracle` extra depend on the `pg` extra. `loaders/elastic.py` (D07) follows the same
  pattern, so this is the house style, not a new one.

## Not verified

* **Cold start of the Oracle container** (`python scripts/dev.py up oracle`): the container was already
  up and healthy when this task started, so the "slow first start / 300s start period" path was not
  exercised here. `docker ps` shows `Up About an hour (healthy)`.
* **The larger default world against every acceptance item**: the CLI was run with the default
  2000-customer world (50 006 events, transcript below) but the pytest suite uses
  `WorldConfig.small()` for speed, so the partition/privilege assertions ran on the small world.
* **Behaviour under Docker memory pressure**: Elasticsearch (D07) held ~1.5 GB and Postgres/API were
  also running; nothing had to be stopped, but this run does not prove Oracle starts on a 7.5 GB VM
  with all services up.
* **Oracle < 23ai**: only 23ai Free is exercised (`v23.26.4.0.0`), so the exact error numbers under
  19c (`ORA-01031` wording, no `ORA-41900`) are not checked. AGENTS.md says the probe must discover
  versions rather than require them; the adapter lane, not D05, owns that.

## Plan issues

* TASKS.md says the read-only rejection is "`ORA-01031`/`ORA-01456` class". On 23ai a missing DML
  privilege is `ORA-41900`, not `ORA-01031`; a future task asserting a literal `ORA-01031` for an
  `INSERT` would fail on the image this repo pins. Worth keeping the family, not the number.
* TASKS.md does not say whether `usage_by_load` / `accounts_hash` belong to the Oracle dataset. D05's
  text names only `usage_events`; the loader loads `usage_by_load` (needed for the event-time versus
  ingestion-time contrast) and skips `accounts_hash`. A later cross-engine eval task should state the
  canonical per-engine table set so D03/D05/D06 do not drift.
