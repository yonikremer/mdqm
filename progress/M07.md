## Summary

Shipped the client side as a Claude Code plugin in `plugin/mdqm/`:

- **`.claude-plugin/plugin.json`** - manifest with `name`, `displayName`, `author` and one
  `userConfig` option, `mdqm_python`, which is the interpreter the context hook runs under.
- **`.mcp.json`** - one `http` MCP server, `"url": "${MDQM_URL}/mcp"`, `Authorization: Bearer
  ${MDQM_TOKEN}`, and `alwaysLoad: true` so the five coarse tools are in context on turn one instead
  of behind a tool-search step.
- **`hooks/hooks.json`** - one `UserPromptSubmit` hook in **exec form** (`command` + `args`, so no
  shell and therefore no bash on Windows), `timeout: 3`.
- **`scripts/context_hook.py`** - the hook: stdlib only, Python 3.9 syntax, reads the `prompt` off
  stdin, posts it to `POST /context`, prints
  `{"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "..."}}`, and
  prints nothing at all on any failure (fail open, exit 0). Writes UTF-8 bytes so the Hebrew pack
  survives a Windows console code page.
- **`skills/mdqm-query/SKILL.md`** - how a weak agent uses the five tools: the spec anatomy, the
  three spec examples (all three validate against the real `QuerySpec` in a test), and what to do
  with an `ErrorResponse`.
- **`plugin/README.md`** - one-step install from an internal marketplace and from a local directory
  (`--plugin-dir`), the two env vars, the interpreter choice, and a troubleshooting table.
- **`tests/unit/test_plugin_hook.py`** - 36 tests: the hook run as a real subprocess against a
  recording stub server, every failure mode, and the plugin files' shape.

## Decisions

1. **Endpoint values come from the environment, not `userConfig`.** `MDQM_URL` and `MDQM_TOKEN` are
   referenced as `${MDQM_URL}` / `${MDQM_TOKEN}` in `.mcp.json`, which the docs verify as expansion
   in a server's `url` and `headers`. A `userConfig`-based token would be prettier (secure storage,
   no shell) but the docs only promise `${user_config.*}` substitution in "MCP server config", and a
   silent non-substitution would send the literal text to the server. Environment expansion is the
   documented, unambiguous path, and it is also what the task's own wording named. The plugin files
   therefore hold no token, no host and no port - one checkout serves every environment.
2. **No `:-default` for `MDQM_URL`.** A default would have to hard-code a host and a port, which the
   task forbids and the test asserts. Unset `MDQM_URL` leaves the text unexpanded, which `/mcp`
   reports as an invalid URL: a visible configuration error, not a silent one.
3. **The interpreter is a `userConfig` option.** Exec form needs a real executable on `PATH`, and
   there is no single name for Python across platforms (`python3` on POSIX, `python` on Windows).
   Shell form would have solved it by string-matching, but Windows' shell is Git Bash or PowerShell
   and quoting would then differ per machine. One prompted option, default `python3`, is honest and
   works everywhere; the README says to set `python` on Windows.
4. **`alwaysLoad: true`.** The docs answer the task's open question: a server-level `alwaysLoad`
   puts a small tool set in context without a search step. Five tools qualifies.
5. **Exec form over shell form**, per the docs' own advice ("set `args` whenever the hook references
   a path placeholder"): each `args` element is passed as one argument, so a plugin path with spaces
   or an apostrophe needs no quoting and behaves identically on all three platforms.
6. **`timeout: 3`, and the script's own `TIMEOUT_SECONDS = 0.45`.** `UserPromptSubmit` blocks the
   prompt, so the wall-clock budget is the point and the process cap is only a backstop. The first
   version used 0.8s and the first integration run caught a real defect: this box does not *refuse*
   a connection to a closed loopback port, it silently drops it, so the connect waits out the whole
   timeout. Measured after the fix: 0.59-0.63s with the server down, against 0.11-0.14s for a run
   that makes no call, i.e. the dead-server cost is ~0.45s (the timeout) and the rest is interpreter
   start. The test therefore asserts both the product promise (`< 1.0s` absolute) and the behaviour
   (`< 0.7s` over a no-call baseline), so it stops being a measurement of how fast the machine
   starts Python. 0.45s is ample for the server, which answered a real pack in ~10ms on loopback.
7. **No `onFailure` key.** It would be `"continue"`, which is already the behaviour, and the field
   needs Claude Code v2.1.295+; omitting it keeps the plugin loadable on older clients for no
   behavioural difference.
8. **The hook never truncates the pack.** Over 10,000 characters Claude Code writes the text to a
   file and shows a 2,000-character preview instead of injecting it. Truncating semantic facts
   silently would be worse than the documented fallback (AGENTS.md principle 10).
9. **`plugin/README.md` is outside `plugin/mdqm/`.** Claude Code loads everything under `plugin/mdqm`,
   so the README lives one level up and is not scanned. A test pins the shipped file set to exactly
   the five documented files.

## Docs verified (formats change; these are what I read, not memory)

Fetched from `code.claude.com/docs` on the day of writing, as `.md` sources:

- https://code.claude.com/docs/en/plugins - a plugin is a directory; manifest at
  `.claude-plugin/plugin.json`; components are skills, agents, hooks, `.mcp.json`.
- https://code.claude.com/docs/en/plugins/components - `hooks/hooks.json` sits under a top-level
  `"hooks"` key in the same shape as `settings.json`; `.mcp.json` is the same shape as a project
  `.mcp.json`; plugin MCP tools are named `mcp__plugin_<plugin>_<server>__<tool>`; plugin hooks
  substitute `${user_config.*}` into `command` and `args` in exec form only; on Windows exec form
  needs a real `.exe` (not a `.cmd`/`.bat` shim).
- https://code.claude.com/docs/en/plugins/manifest-reference - field table; `userConfig` is a strict
  object of `type`/`title`/`description`/`required`/`default`/`options`/`multiple`/`sensitive`;
  `${user_config.KEY}` substitution scope; `CLAUDE_PLUGIN_OPTION_<KEY>` is exported to hook
  processes; shell-form hooks and `headersHelper` reject `${user_config.*}`.
- https://code.claude.com/docs/en/hooks - `UserPromptSubmit` has **no matcher support** and a
  lowered 30s default timeout because it blocks the prompt; stdout JSON on exit 0 with
  `hookSpecificOutput.additionalContext` is the documented context channel; plain-text stdout is
  also injected; exec form vs shell form (`args` present -> no shell, no tokenisation, `${...}`
  substituted as plain strings); over 10,000 characters is written to a file; a timed-out hook's
  output is discarded and the prompt still proceeds.
- https://code.claude.com/docs/en/mcp - `${VAR}` and `${VAR:-default}` expansion in a server's
  `command`, `args`, `env`, `url` and `headers`; `alwaysLoad` on any server type; `headersHelper`
  runs in a shell with a 10s give-up and must print a JSON object of headers.
- https://code.claude.com/docs/en/skills - `SKILL.md` frontmatter is read only when `---` is the
  file's **first line**; the field table (`name`, `description`, `when_to_use`, `allowed-tools`,
  `license`, `compatibility`, `metadata`, ...); a plugin skill is `skills/<dir>/SKILL.md` and runs as
  `/<plugin>:<dir>`.
