## Summary

`src/mdqm/adapters/oracle.py` is the Oracle `SourceAdapter` in **thin mode** (`oracledb`, no Oracle
Client, `oracledb.is_thin_mode()` reported by the probe), registered through the `mdqm.adapters`
entry point:

* a pooled connection per source (`options.user` is the per-person login, the password comes from
  `SourceConfig.secret` through the secret provider, never from config);
* a read-only session (`SET TRANSACTION READ ONLY` re-issued before every execution, because Oracle
  ends it with the transaction) plus `ALTER SESSION SET TIME_ZONE = 'UTC'`;
* `extract_catalog()` from `ALL_TAB_COLS` / `ALL_CONSTRAINTS` / `ALL_IND_COLUMNS` / `ALL_TABLES` /
  `ALL_VIEWS`, with the accounts Oracle itself maintains excluded through
  `ALL_USERS.oracle_maintained` (data-driven, not a hard-coded schema list);
* `extract_partitions()` from `ALL_PART_TABLES` / `ALL_PART_KEY_COLUMNS` / `ALL_TAB_PARTITIONS`: the
  interval-partitioned tables D05 loaded report the partitions Oracle derived from the data and
  their **real bounds** (each lower bound is the previous partition's `HIGH_VALUE`);
* `execute()` returning an `ArrowStream` of `pyarrow.RecordBatch` with `max_rows`/`max_bytes`
  honoured while fetching, `cancel()` that really interrupts, and a deadline;
* `explain()` from `EXPLAIN PLAN` + `PLAN_TABLE` (verbatim text from `DBMS_XPLAN`), with the pruning
  proof: numeric `PSTART`/`PSTOP` = `proven`, `PSTART = KEY` = `unproven`;
* `mine_queries()` from `V$SQL` where the account may read it, `NotSupported` with the capability
  name where it may not; `mutability_stats()` always `NotSupported` (see Decisions).

## Decisions

* **The deadline is a watchdog that calls `Connection.cancel()`, not `call_timeout`.** This is the
  one place where the obvious API is wrong: with a 1 s `call_timeout` the interrupt fires, but the
  driver then has to drain the response, and on a slow statement that drain times out in turn --
  `DPY-4011: the database or network closed the connection` -- so the session is gone. That is the
  opposite of the acceptance ("a timeout cancels a slow statement and the connection is reusable").
  Measured both ways on oracledb 26.2.0 before choosing: `cancel()` produces `ORA-01013` in 1.0 s and
  the same connection answers afterwards, `call_timeout` produced `DPY-4011` and a dead session.
  `Connection.call_timeout` is therefore only a backstop, set `CALL_TIMEOUT_BACKSTOP_MS`
  (=5 s) beyond the deadline, and a `DPY-4011` that arrives after the deadline is still translated to
  `OracleTimeout` (with the session loss in the message) so a caller never sees a raw driver error
  for a deadline it asked for.
* **`mutability_stats()` is `NotSupported`, not implemented.** `ALL_TAB_MODIFICATIONS` exists and is
  readable (`SELECT` works, measured), but it is refreshed by `DBMS_STATS` -- a stats gather or an
  explicit `FLUSH_DATABASE_MONITORING_INFO` -- and this adapter must not gather statistics on
  somebody's primary. Between gathers a table that changed all night reads as unchanged, so the
  pipeline's checksum fallback is the safer answer. The capability is reported `unsupported` with
  that reason in the probe, so the fallback is chosen knowingly.
* **`mine_queries()` is implemented.** D05 grants `MDQM_RO` `SELECT` on `V$SQL`, so the real thing is
  available. Counters in `V$SQL` are cumulative per child cursor; `mean_time_ms` is derived from
  `total_time_ms / calls`. `RawQuery.user` is left `None`: `PARSING_SCHEMA_NAME` is who parsed the
  statement, not who ran it, and naming the wrong person is worse than naming nobody.
* **`USER` stays `None`-able but the adapter requires `options.user`.** A shared login defeats the
  audit requirement, so a config without a user is a `OracleConfigError` naming `options.user`.
* **Arrow types follow the declared precision.** `NUMBER(12,0)` -> `int64` (money and counts stay
  exact), `NUMBER(19,0)` -> `decimal128(38,0)` (19 digits can exceed `int64`), `NUMBER(p,s>0)` ->
  `decimal128(38,s)`, an unconstrained `NUMBER` -> `float64` (an aggregate like `AVG` reports no
  declared scale; a fixed decimal would fail loudly on a value the engine is happy to produce).
  Consequence worth knowing: Oracle's `COUNT(*)` comes back as `double`, because the description
  carries no precision. It is exact for any realistic row count and compares equal across engines.
* **Column names are Oracle's (upper case).** `SELECT client_no ...` yields `CLIENT_NO`; the adapter
  does not fold names, because the catalog reports the same upper-case identifiers and the drift
  comparison must see one spelling.
* **Catalog excludes Oracle-maintained accounts** with `ALL_USERS.oracle_maintained = 'Y'`, and skips
  temporary/global-temporary tables, nested tables, `IOT` overflow segments and recycle-bin objects.
  Without the exclusion the "catalog" of `MDQM_RO` is mostly `SYS`/`XDB` dictionary base tables
  (measured: `ALL_TABLES` listed them through public grants).
* **Interval granularity is parsed from `ALL_PART_TABLES.interval`** (`NUMTOYMINTERVAL(1,'MONTH')` ->
  month, `(3,'MONTH')` -> quarter, `NUMTODSINTERVAL(1,'DAY')` -> day); an interval that has no
  granularity in the model stays `None` while the bounds are still reported.
* **Composite (sub)partitioning raises `NotSupported`** naming `partition_metadata` instead of
  describing half of it, and so does a strategy with no planner equivalent (`REFERENCE`).

## Not verified

* **`DPY-4011` from a `call_timeout` backstop**: observed repeatedly while developing the first
  version (that is why the design changed), but the *translation* of a post-deadline `DPY-4011` to
  `OracleTimeout` is covered only by a unit test with a synthetic driver error -- it cannot be
  produced on demand now that the backstop sits 5 s beyond the deadline.
* **Oracle versions other than 23ai Free** (`v23.26.4.0.0`): the plan table the read-only account
  needs (`SYS.PLAN_TABLE$`, a `SYS$SESSION` GTT with `PUBLIC` DML grants) is the 12c+ shape; on an
  instance where that grant is missing, `explain()` raises `NotSupported` (there is a code path for
  it) but that path was not exercised against a real locked-down instance.
* **`V$SQL` readable but huge**: `mine_queries` reads the whole view for the window (one row per
  child cursor). Fine at the ~10^3 rows of a dev instance; an organisation with a large shared pool
  would want paging or an elapsed-time threshold, which is a later task's decision.
* **A `SYSTEM`-partitioned table** (no key columns) is mapped to `strategy=expression` by the unit
  tests only; the D05 schema has none.
* **`mutability_stats`**: not verified against data, because it is not implemented by design.

## Plan issues

* TASKS.md asks for "explain via EXPLAIN PLAN + DBMS_XPLAN (document what a read-only account
  needs)". The answer, measured: on 23ai nothing -- `PLAN_TABLE` is a public synonym for
  `SYS.PLAN_TABLE$`, a session GTT with `PUBLIC` insert/update/delete/select. On an older or
  locked-down instance the account needs those grants, so `explain()` reports `NotSupported` rather
  than failing. This belongs in DESIGN's oracle notes, not only in this ledger.
* `Partitioning` carries no table name, so `extract_partitions()` returns a list whose entries cannot
  be attached to a table by a caller that has several sources. The PostgreSQL adapter has the same
  limitation and works around it by ordering; `partitions_total` in `PlanSummary` was therefore
  counted with a separate catalog query for the fragment's single table. A `table` field on
  `Partitioning` would remove that special case for every adapter.
* **Incident in this worktree, recorded because it changed a status**: a commit appeared on this
  branch (`da37339`, author "Yoni") that marked the timeout test `xfail(strict=True)` and wrote a
  `progress/A07.md` claiming `DPY-4011` made the item unprovable, that only 18 of 19 integration
  tests pass, and that `mine_queries` is `NotSupported`. Those claims contradict the measurements
  here (the timeout item is proven, `mine_queries` is implemented and reads `V$SQL`), and the
  strict `xfail` was failing the suite (`1 xfailed` on every run). The marker and that ledger were
  replaced with the measured results; the commit stays in history so the correction is visible.
