## Summary

`mdqm.context.index` is the searchable view of the semantic layer that `find_data` hits. One document per
**table, column, measure, categorical value, approved join and approved example query**, with four ranked fields
(title, names, labels, body) and bm25 weights `(6, 3, 2, 1)`. Hebrew and English labels, every value map's
canonical values and synonyms, and the deployment's own names for measures/tables (`labels=` input) all reach the
`labels` field; the same label groups are stored in `context_synonym`, so the query side expands too. Query terms
are folded with the existing `normalize_label`, prefix-matched, and each Hebrew one-letter prefix (`ה ו ב ל מ כ ש`)
is added as an extra OR-variant — never a replacement. FTS5 with `unicode61 remove_diacritics 2` is created lazily;
when the H01 probe reports FTS5 missing, the same documents are searched with a `LIKE` scan and hits carry
`score=None`. A rebuild is incremental by `SemanticLayer.version_hash` (unchanged hash → nothing written). Searches
with zero hits are appended to `empty_searches` and read back with `unmatched()`.

New migration `0004_context_index.sql` adds `context_document`, `context_synonym`, `context_index_state` and
`empty_searches`. The FTS5 virtual table is deliberately not in a migration (a build without FTS5 would fail the
migration and take the audit log and history with it) — it is created inside the index's own write transaction,
the same rule H03 follows.

## Decisions

- **`labels=` input for the two-language names of measures/tables/columns.** The semantic models carry Hebrew only
  inside `ValueMap.synonyms`; `Measure`, `TableSemantics` and columns have no label field, and editing
  `semantic/models.py` is another lane's file. So the index takes `{"measure:<name>": [...], "table:<source.table>":
  [...], "column:<source.table.column>": [...]}`, validates every key against the layer and the catalogs, and
  raises `ContextIndexError` on an unknown key (an ignored label would be a search that mysteriously misses). This
  is what the curated YAML can feed later; it is documented in the module docstring.
- **Approved examples are an explicit input (`ApprovedExample`)**. The layer has no examples section yet (H05 owns
  their presentation), so the index takes `name`, `question`, `ref` instead of inventing a field in the layer.
- **Hits expose `score: float | None`.** bm25's score when ranked; `None` in the `LIKE` fallback, so a caller
  cannot mistake "unranked" for "score 0.0" and mis-order its Context Pack.
- **Table bodies carry pruning facts only** (key, time columns, partition key, mutability, cache), not a repeat of
  each column's measure note. bm25 sums every matching field, so repeating a measure's name in the table's body
  made `erp.customers` outrank the measure for the query "credit limit". The association still lives where it
  belongs: in the column document's body and in the names field.
- **A synonym group with one label is not stored**, and a query term with no letter or digit (e.g. `"?!")` is
  treated as "no word" and refused: FTS5 would match no token, which is not the same as "no results".
- **Prefix stripping needs a remainder of at least 3 characters**, so `של` is not reduced to `ל` (documented as a
  shortcut: two-letter prefixes such as `מהלקוחות` are out of scope).

## Plan issues

- Tasks H04/H05 assume the semantic layer names its facts in both languages for measures, tables and columns, but
  `semantic/models.py` (C04) has no such field — only `ValueMap.synonyms`. Either a later task adds
  `labels`/`synonyms` to `Measure`/`TableSemantics`, or every deployment must supply them out of band as this task
  does. Worth an explicit backlog decision before H05 hardens the pack format.
- `examples/semantic_example.yaml` has no `tables.crm.customers` entry, so without a catalog the index only learns
  that table from the measures/value maps that reference its columns. That works, but the pipeline (D1) supplying a
  catalog is what makes column types and comments searchable.
