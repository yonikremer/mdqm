## Summary

Stage D8 (`src/mdqm/pipeline/stages/conversions.py`) rediscovers a measure's conversion from data and
hands it to the human gate. No new framework, no new dependency, no second vocabulary:

- **A small, declared hypothesis space** and nothing else: a scale from `SCALES`
  (`1, 0.001, 0.01, 0.1, 10, 100, 1000`), an optional rounding step from D5's `GRANULARITY_LADDER`
  (imported, not copied), a mode (`half_up` | `half_even`), and the **order of operations**
  (`scale_then_round` = `ROUND(x*k/g)*g`, `round_then_scale` = `ROUND(x/g)*g*k`). Every candidate
  renders to a normalize template that `mdqm.semantic.measures.check_normalize_template` accepts, so
  what D8 proposes C06 can execute. Collapses (`k=1` makes the two orders identical, `step=None`
  needs no mode) are applied when enumerating, so the runner-up list is not the same formula twice.
- **Scoring is the exact match rate on aligned pairs**, in `Decimal`/integer maths through C06's
  `round_to_multiple` — the detector and the SQL it proposes agree at the `.5` boundary.
  `candidate_key` is a total order: match rate, then simplicity rank (identity < scale < round <
  round+scale), then the coarsest step, then the smaller scale, then `half_up` before `half_even`.
- **Counter-examples are first-class**: the rows a hypothesis misses are reported per pair
  (`CounterExample`, capped and sorted), which is what the review queue shows a human.
- **Outcomes are honest**: `identity`, `converted`, `no_hypothesis`, `insufficient_data`. Below the
  threshold (or under 3 usable pairs) the stage reports the best attempt *with its poor rate* and
  proposes nothing.
- **The stage** (`ConversionStage`, `name="D8"`, `heavy=True`, `inputs_hash`, `run`) declares pairs of
  columns (`ColumnPair(reference, other)` with the entity key on each side), reads one bounded sample
  per side through D5's own `sample_query` + `Limits` (no second profiling mechanism), aligns the two
  samples on the entity key, builds the `reference`/`other` Arrow batch and calls the detector's
  Arrow entry point (`detect_pairs`). Detections become `MeasureProposal`s (template, step, mode,
  confidence, evidence, counter-examples) and go to `ReviewQueue` (S12) — `curated/` has no write path
  here and none is created.
- Entity keys are compared by meaning: `billing.client_no = "00…01"` joins `crm.cust_id = 1`, which
  is the same zero-pad format conversion D7 reports. A duplicated key on the other side is counted
  once and reported in `skipped`.

What it recovered from the D02 world through F05's in-process DuckDB adapters (three columns only,
nothing told): `billing.accounts.credit_limit -> crm` = `ROUND({col} / 5000) * 5000`,
`step=5000`, `mode=half_up`, 199/199 pairs (100%, the planted NULL dropped); `erp.customers_erp.limit_k
-> crm` = `{col} * 10`, 199/200 (99.5%) with the planted erp exception as the one counter-example
(`other=1000`, `reference=5000`, `predicted=10000`); `crm.credit_limit` is identity because it is the
declared reference. `erp.limit_k` vs `crm.cust_id` (a decoy) = `no_hypothesis`, best 1%.

## Decisions

- **The threshold decides whether to propose, never whether to approve.** The task said "accept
  automatically only above a threshold"; DESIGN.md section 10 and AGENTS principle 3 put *every*
  conversion behind a human, so there is no auto-approve path. `DEFAULT_MIN_MATCH = 0.99` (not the
  0.995 the acceptance mentions as a *result*): the world plants real exceptions (0.5-1% of rows)
  that must not push a true conversion out of range, while a genuine mismatch scores near zero. The
  number is a constructor argument, so a deployment can tighten it.
- **A pair is ordered: `reference` (canonical units) and `other` (to convert).** Which column is
  canonical is a declaration the pipeline already has (the column the semantic layer names), not
  something the data can settle: `erp * 10` and `crm / 10` explain the same rows, so inferring the
  direction would have invented the answer. Which columns mean the same field stays D7's question.
- **An exact tie between two formulas is named, not hidden.** A no-op ROUND fits any column already
  on that grid, so the erp pair ties 28 ways (e.g. `ROUND(x*10/5000)*5000`); the note says so and the
  simplest claim (pure scale) wins the ranking.
- **Money never touches a float.** Pairs are `Decimal`; a `float` column is read via `repr` (it lost
  exactness at its source already) and a non-numeric or NULL value is dropped and counted
  (`pairs_dropped`), never treated as a mismatch or silently averaged over.
- **Pairs are sorted before the cap** (`DEFAULT_MAX_PAIRS = 2000`) so a bounded detection is
  reproducible whatever order the source returned rows in; counter-examples are sorted too.
- **`inputs_hash` includes the date of `exec_ts`**, exactly as D5: values that change daily are not
  the same fact tomorrow, so a nightly pass re-detects and two passes on one day agree.
- **Confidence is the observed match rate**, computed by a validator, never a model's opinion
  (DESIGN.md section 10).

## Deviations

- "Accept automatically above the threshold": not implemented as auto-approval, see Decisions. Below
  the threshold the outcome is `no_hypothesis`; at or above it the result is a proposal awaiting a
  human. Rejected conversions are remembered by S12's negative memory, which the stage relies on by
  re-submitting every night (`not asked again (suppressed)` appears in `skipped`).
- "Extra hypotheses may come from mining hints (S08)": not wired. S08's conversion-expression hints
  only *raise the prior* per DESIGN.md section 10, and ordering by prior is not needed to meet any
  acceptance item, so the space is data-only for now. Nothing in the design depends on it.
- The proposal patch sits on the measure item (`field=""`, `patch={"sources": {<column>:
  {"normalize": ...}}}`) rather than on `sources.<column>`: `ReviewQueue._approved_patch` merges the
  approval provenance into the patch's own root, so a deeper field would record `approved_by` as if
  it were a source column. Shape verified against `_assign`/`_merge`; see Plan issues for the gap
  that remains.

## Plan issues

- **S12 gap (not my lane).** `ReviewQueue._approved_patch` attaches provenance to the patch root and
  `_assign` merges a nested mapping by *replacing* it, so approving a second D8 proposal for the same
  measure rewrites `measures.<m>.sources` and drops the first source. A measure with three sources
  needs three approvals, so this will bite as soon as the pipeline proposes more than one column of
  one measure. Suggested fix for S12: deep-merge mappings in `_assign`, and let a proposal name a
  dotted *item* path that is not split (e.g. a `path` tuple field) so `sources.<dotted column key>`
  is addressable.
- Nothing in the backlog says where the **pair list** for D8 comes from. S07 finds join candidates
  but does not hand over paired columns, and `TASKS.md` has no task for "sample aligned pairs". D8
  therefore takes the pairs as a declaration; a follow-up task should build them from D7's approved
  joins so the stage can be scheduled with no human input at all.
