## Summary
An image built with `MDQM_EXTRAS=pg,mssql` now provably talks to the compose SQL Server from inside the
container: `mssql_python.connect(server="mssql", …, uid="mdqm_ro")` answers `('erp', 'mdqm_ro', 201)`,
and `SELECT COUNT(*) FROM sys.dm_db_partition_stats` answers 201, so the size reader's
`VIEW DATABASE STATE` grant works through the image too. `entry_points(group="mdqm.adapters")` inside
the image lists all five adapters, so the extra is really installed rather than merely importable.

## Found on the way: the runtime image shipped an installer
`pip uninstall --yes pip setuptools wheel` runs in the **builder** stage, which only clears the venv.
The base image's own pip stayed in the runtime layer and was first on no PATH but reachable:
`pip -> /usr/local/bin/pip` (`pip 25.0.1 from /usr/local/lib/python3.12/site-packages/pip`). That makes
the Dockerfile's "no installer in the runtime image" comment false and lets a container that mounts a
wheelhouse install anything at run time — an air-gap hole (AGENTS.md principle 7). Fixed in the runtime
stage: `/usr/local/bin/pip*` and the base `site-packages/pip*` are removed. Re-measured on the rebuilt
image: `pip -> None`, `import pip -> No module named 'pip'`. The same probe on `mdqm/server:dev`
(the default `pg` image) answers `None`.

## Decisions
* The proof runs the image on the **compose network** (`--network mdqm_default`) with the deployment's
  own env, not a host-side `mssql_python` call: the question was packaging, so the answer has to come
  from inside the container.
* A temporary compose override (`a10.override.yml`, deleted before the commit) was the way to hand the
  container `.env` without the agent ever reading the secret file: Compose reads it, the probe process
  receives it, nothing is printed.
* The default image stays `MDQM_EXTRAS=pg`. A10 is the opt-in image, not a new default.
