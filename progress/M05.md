## Summary

The three lookup tools got real bodies in `src/mdqm/server/tools/misc.py`, and M01's single
`tools.py` became the package `src/mdqm/server/tools/` that the task plan (`owns`:
`tools/misc.py`, `tools/query.py`, `tools/find_data.py`) assumes. `get_more`, `history` and
`feedback` now:

- page a stored result through C15's `ResultStore.get_more` with the **caller's** id as owner, so a
  handle is a pointer to your own rows and nothing more;
- list and search H03's history through `recent(user_id=...)` / `search(..., user_id=...)`, and turn
  `rerun_id` + `rerun_mode` into H03's `rerun(...)` plan (frozen = the stored `exec_ts`, relative =
  the injected clock);
- write one row to a new `query_feedback` table (migration `0007_feedback.sql`, `FeedbackStore` in
  `src/mdqm/store/feedback.py`).

Every refusal is a structured `ErrorResponse` with the new code `NOT_FOUND` (unknown, expired and
somebody-else's id are byte-identical, so a handle cannot be probed for existence) and is appended
to H02's audit log as a `BLOCKED` row. 16 tests cover paging 10k rows into every row exactly once,
the cross-user handle, history scoping with a Hebrew search, frozen vs relative re-run through the
tool, the persisted rating, the scrubbed rating text, and one real MCP roundtrip on loopback where
the handler sees each caller's own identity.

## Decisions

1. **One `NOT_FOUND` code, one builder.** The taxonomy had no code for "nothing readable under this
   id", and reusing `INVALID_SPEC` would tell the agent to fix a spec field it never sent. So
   `ErrorCode.NOT_FOUND` + `errors.not_found(what, fix)` were added following the module's own
   documented rule ("extend the enum, add the builder, add the case to `tests/unit/test_errors.py`").
   The `problem` text is built from `what` alone — never from the id.
2. **Stores are injected once per process, not per call.** The tool signatures *are* the MCP wire
   schema, so a `services` argument would leak into the JSON schema a weak model reads. Instead
   `configure_services(ToolServices)` / `current_services()` / `reset_services()` hold the four
   stores (handles, history, feedback, audit). This is a deliberate, narrow exception to "no global
   mutable state": a ContextVar was rejected because `threading.Thread` does not inherit context, so
   a threaded uvicorn server would silently answer `not_implemented`.
3. **No stores -> `not_implemented`, with the reason.** A server built without them answers
   `status="not_implemented"` plus `problem`/`fix` naming the missing piece, instead of an empty
   result or an exception. That keeps M01's stub contract test meaningful and makes a wiring mistake
   report itself.
4. **`query_id` is a run id.** `feedback` accepts `"12"` and `"q_12"` and resolves them against the
   caller's own history; anything else, and another user's run, is `NOT_FOUND` (one message). No
   feedback row is written for a run the caller does not own.
5. **The queue has no triage column yet.** `FeedbackStore.recent()` is the consumer's read path; a
   "consumed/triaged" state belongs to whoever consumes it (S12 review queue / mining), and shipping
   an unused column plus an untested setter would be speculative.
6. **Free text rating is scrubbed, not refused.** `corrected` goes through H03's `_redact` (one home
   for "what looks like a credential") and is then bounded to 4000 chars: a rating with a pasted
   token must not become the way a secret reaches the metadata file.

## Deviations

- **File layout.** M01 shipped all five tools in `src/mdqm/server/tools.py`; TASKS.md gives M02/M03/
  M04/M05 one module each under `src/mdqm/server/tools/`. `tools.py` became
  `tools/__init__.py` (still holding `find_data`, `query`, `NotImplementedResult`, `TOOL_FUNCTIONS`,
  `register_tools`), and the three implemented bodies live in `tools/misc.py`. M02/M03 can now add
  `tools/find_data.py` and `tools/query.py` without repeating this move.
- **Files edited outside `owns`** (each minimally, listed so it is reviewable):
  `src/mdqm/errors.py` (enum + builder + `BUILDERS` + the docstring table),
  `tests/unit/test_errors.py` (two `NOT_FOUND` cases + the published code list),
  `tests/unit/test_server_skeleton.py` (only the three changed argument dicts in `TOOL_CALLS`),
  `src/mdqm/server/schemas.py` (`newline="\n"` so regenerating the JSON on Windows no longer
  rewrites every line as CRLF — the file is generated and was 100% churned by it),
  and `docs/tool-schemas.json` (regenerated, as the drift test requires).
- **The server does not yet build `ToolServices`.** `create_server()`/`serve()` still start with no
  stores, so a served process answers `not_implemented` for these three tools until the wiring task
  does the following (one call, no signature change):
  `configure_services(ToolServices(handles=governor.store, history=HistoryStore(store), feedback=FeedbackStore(store), audit=AuditLog(store)))`
  after opening `Store(settings.paths.metadata_db)` and initialising it. This belongs with M03, which
  builds the `query` path and the `Governor` whose `store` these handles come from; doing it here
  would have duplicated M03's service wiring and invited a merge conflict in `app.py`.

## Not verified

- No container runtime and no live data source on this box, so nothing here ran against Postgres or
  the DuckDB fake adapter: the store the tools read is a `tmp_path` SQLite and the rows are a
  `pyarrow` table put into the real `ResultStore`. Paging, ownership and TTL are C15's, tested there.
- `migrations/0007_feedback.sql` was applied to fresh test databases only. An upgrade of an existing
  metadata DB (schema version 5 -> 6) is exercised by the migration machinery, not by this task.
- The migration number moved from `0006` to `0007` during integration: S12's review queue merged
  `0006_review.sql` first, and `load_migrations` refused the duplicate loudly ("two migrations claim
  version 0006") — exactly the failure it is meant to raise. Renumbered here; nothing depends on it.

## Plan issues

- `TASKS.md` gives M05 the signature `history(text?, rerun_id?, rerun_mode?)`, which has no way to
  ask "just give me a run id": solved with `rerun_id=None` meaning "list", and `limit` added for
  parity with the other tools.
- `feedback(query_id, ok, corrected?)` cannot express the stub's earlier `rating: 1..5`, so the two
  wire formats differ; `docs/tool-schemas.json` is regenerated and the M01 contract test updated.
- Observation for the C15/C16 lanes, not fixed here: `ResultStore.get_more` can return fewer rows
  than `limit` because the page is built through `summarise`, whose token budget shrinks the sample
  (a 1000-row page near the budget returned 974). No row is lost — `next_offset` is computed from
  the rows actually delivered — but a short page is not reported as "short", only as `truncated`.
  Worth a `page_shortened` flag if a caller ever needs to tell "the result ended" from "the budget
  cut this page".
