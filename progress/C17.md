## Summary

Built `src/mdqm/executor/` (the E03 engine): `FederatedPlan` + `FederatedExecutor` take one compiled
fragment per source, run each through `Governor.execute` (never an adapter directly), reuse a whole
fragment from a DuckDB cache when fresh, cap each fragment (rows/bytes -> `COST_TOO_HIGH` + a narrowing
`fix`, before any join runs), register the Arrow results as relations in the executor's own DuckDB,
and answer with one sqlglot-built statement over them (the approved join's ON clause with its key
conversion, `inner`/`left`/`semi` shapes, local per-source normalisation, grouping, aggregates).
`QualityReport` carries rows + `fetched_at` per source (cache hit included), `matched`/`dropped`/
`multiplied`/`dropped_keys` per join, NULL groups per grouping column, normalisation sanity violations,
and `complete=False` with no table when a source failed.

Proven against three F05 fake adapters holding the D02 world (crm/billing/erp), pinned to the E01
world hash: the cross-source `avg credit_limit_r5000 by customer_status` equals the canonical ground
truth and E01's `avg_limit_by_status_crm` rows exactly; each storage form normalised locally
reproduces E01's per-source answer (identity / `ROUND(x/5000)*5000` / `x*10`); the usage-by-status
cross-source question reproduces E01's `usage_units_by_status_window` rows and reports the in-window
orphan `client_no` rows the inner join dropped (45 of the 200 planted, recomputed from the world);
erp's 6 planted duplicate keys are reported as `multiplied` when joined for rows; a second identical
call makes zero adapter calls and reports per-source freshness; a failing source yields no answer.

## Decisions

- **The plan is explicit**: fragments + joins + output, not a multi-source spec split. The spec model
  (C04) is single-source and the compiler (C09) compiles one source, so a "split" has nothing to
  split yet. Who builds the plan is M04; C17 owns the execution and the report. Recorded in the
  module docstring.
- **Local normalisation, not source normalisation, for row values.** The compiler normalises only an
  aggregate it emits itself, so a fragment cannot hand back a normalised per-row measure. So the plan
  declares `LocalAggregate(column, measure)`, and the executor renders that measure's per-source
  template (same semantic-layer template, same rounding mode) over the landed column.
- **Join shapes `inner` / `left` / `semi`.** `semi` (EXISTS) exists because a partner joined only for
  its existence must not fan out: erp carries duplicate rows on purpose, and a row-producing join
  there doubles customers and answers a different average. Multiplication is reported either way, so
  an inflation cannot pass unnoticed.
- **A step can declare `dedupe_on`** (the table's declared key): duplicate rows are dropped by
  `SELECT DISTINCT ON (...)` and counted in `deduplicated`, instead of silently multiplying joins.
  This is what makes the erp average match E01's deduped oracle.
- **The cache stores a whole fragment**, keyed on source + table + fragment SQL + semantic version,
  judged by C12's `is_fresh_at` with a zero span (a whole-table read has no window, so it gets the
  floor TTL, the conservative reading). C14's partition-window `SegmentCache` is deliberately *not*
  re-implemented: two cache rules that disagree would be worse than one. "Freshness per segment" is
  therefore reported per step (`fetched_at`, `cache_status`, `age_s`), which is the granularity a
  whole-fragment cache has.
- **Caps are checked with one row of headroom** (`max_rows + 1` to the governor), so a result exactly
  at the cap is not mistaken for a truncated one; the caps are re-checked on a cache hit so a limit
  that shrank cannot be bypassed by the cache.
- **Failures are values**: a governor refusal returns its `ErrorResponse` and no table; a local DuckDB
  error (plan and fragments disagree = our bug) returns `INTERNAL_ERROR` with a correlation id.
- `NullGroup.rows` counts source rows (queried per grouping column on the step relation) rather than
  answer rows: a grouped answer collapses every unmapped code into one NULL row, which would understate
  how much data is affected.

## Deviations

- **Two files outside `owns`, both minimal and deliberate**:
  - `src/mdqm/governor/handles.py`: added `ResultStore.table(handle, *, owner) -> pa.Table`. The
    executor needs the rows, and paging them back through `get_more` would convert them to JSON
    (timestamps become strings) before the join. Same ownership/expiry checks as `meta`.
  - `src/mdqm/testing/fake_adapter.py`: added `SET TimeZone='UTC'` at open. Without it the fake's
    session zone is the host's (Asia/Jerusalem here), and a naive `TIMESTAMP` literal compared with a
    TIMESTAMPTZ column is read in the session zone -- so every time window silently shifted by the
    host offset (the cross-source usage sum came out 98 units over E01's independently derived
    answer). This was a real fidelity bug in F05 that would have hit the E03 integration; a source
    session is UTC. No other test changed behaviour.
- The design is unchanged (`docs/DESIGN.md` sections 3/8/9 already describe this executor), so no doc
  edit.

## Not verified

- **Against three real Postgres databases.** No container runtime on this machine (no Docker/Desktop/
  Rancher/Podman, WSL2 store broken), so everything is proven on three F05 fake adapters -- one per
  logical source, each a real in-process DuckDB -- and never against `docker-compose --profile pg`.
  Specifically unverified: PostgreSQL's own timestamp/type round-trip through `psycopg`, real
  `EXPLAIN`/partition behaviour on the billing fragment, and driver-level cancellation inside the
  governor's deadline. The acceptance items are met on the fakes; the Postgres run belongs to E03.
- The integration test for this lane does not exist (D01 has no services here); no
  `tests/integration` marker was added.
- A windowed fragment is cached whole for the floor TTL only; partition-aligned reuse across two
  different windows is C14's `SegmentCache` and will need wiring when M04 builds plans from specs.

## Plan issues

1. **`FragmentStep` takes a `Fragment`, so the plan cannot see `CompiledQuery.output_columns`.** The
   `ColumnCheck` consistency check therefore uses a substring test on the SQL (marked `shortcut:` in
   the code). Once M04 builds plans from `CompiledQuery`, pass the output columns and drop it.
2. **The compiler emits a cross-source join inside one fragment** (`compile_spec` INNER JOINs the
   partner's physical table), which only works when both tables are reachable from one source -- true
   for the all-in-one fake, false in the real deployment. A spec that names an approved join whose
   other side lives in another source should be refused by the compiler with a pointer to the
   federated path, or split by M04. Worth a task.
3. **`FakeAdapter.for_world` puts all three storage forms in one adapter**, which hides exactly the
   cross-source problems this task is about (and lets the compiler's single-fragment join "pass").
   A `for_sources(world)` variant returning one adapter per logical source would make the fake honest.
4. **E01's `usage_units_by_status_window` answer is only reachable when the source session is UTC**;
   before the fake-adapter fix the eval oracle and the fake adapter disagreed by the host offset. Any
   adapter lane that opens a session must pin UTC, or the eval answers drift with the machine's zone.
