## Summary
`src/mdqm/pipeline/core.py` is the framework every D-stage runs on: a `Stage` is any object with
`name`, `inputs_hash(ctx)`, `run(ctx)` (plus optional `heavy` and `sources` declarations).
`run_pipeline()` runs stages in order and skips one whose input hash matches its last successful run
*and* whose recorded output still exists on disk, so a model is never asked again.
Every attempt lands in the new `pipeline_run` ledger (migration `0007`) with its counts, its skips,
its applied fixes, its output paths and, on failure, one bounded line of error.
A stage buffers its YAML sections through `PipelineContext.write_generated`; the runner commits them
after the stage returns, through `mdqm.semantic.writer.write_generated` (temp file + atomic replace),
so a crash leaves `generated/` byte-identical. `curated/` has no write path at all.
Heavy stages wait for a configured `QuietWindow` (refused with the next window start in the message,
`--force` overrides) and take per-source slots from `SourceGate`: at most 1-2 concurrent calls per
source, and no new call when the median of the last three latencies passed the ceiling.
`src/mdqm/pipeline/cli.py` adds `mdqm bootstrap run [--stage X] [--source Y] [--force]`.

## Decisions
- **Ledger table `pipeline_run`** (migration `0007`, the next free number after S12's `0006`) with
  status `ran | skipped | refused | failed`. Only `ran` unlocks a later skip, so a failed attempt can
  never look like success; `skipped`/`refused` attempts are recorded too, because "why did last night
  do nothing?" is the question an operator actually asks.
- **Output is buffered per stage, not streamed.** A stage calls `ctx.write_generated(section,
  payload)` and the *runner* writes it after `run()` returns. This is stronger than temp-file-then-
  rename inside the stage: a crash writes nothing at all and leaves no `.tmp` behind. Each commit
  still uses the existing atomic writer, so a half-written YAML section is impossible either way.
- **A hash match is not enough to skip**: the recorded output paths must still exist. An operator who
  deleted a section expects it back, not "unchanged".
- **The runner owns `status`, `inputs_hash`, `outputs` and `forced`** in a report; a stage supplies
  `counts`, `skipped`, `applied_fixes`. A stage therefore cannot excuse itself from the ledger by
  claiming it was skipped.
- **Quiet windows**: the pipeline takes the *window list* (not `Settings`) and mirrors
  `Settings.is_quiet`'s reading that no configured window means unrestricted. The window arithmetic
  stays in `mdqm.config.quiet.QuietWindow`; only "when does the next one open" is new code.
  A zero-length window (`start == end`) never opens, so the refusal says so instead of promising a
  time that never arrives. A refusal stops the whole pass (nothing interleaves with heavy work).
- **Only heavy stages take a source slot.** Light catalog reads are not gated; the pass is
  single-threaded, so the gate exists for stages that fan out. Defaults: `max_per_source = 2`
  (DESIGN's "1-2"), latency ceiling 30 s measured as the **median of the last 3 calls**, so one slow
  query does not stop the night but a uniformly slow source is left alone.
- **`--source X`** narrows the pass: a stage that declares other `sources` is reported skipped and is
  *not* written to the ledger (it never ran), while a stage with no declaration runs for any source.
- **Exit codes** for a nightly job: `0` ran/skipped **and** deferred-to-window, `1` failed, `2` an
  unknown `--stage`. Deferral is not a failure.
- `next_quiet_start` lives in `core.py` although `QuietWindow` owns quiet logic: `owns` for S01 is
  `core.py` and the test file, and adding a method to F03's module would collide with that lane for
  no gain. If F03 ever wants it, `QuietWindow.next_start` is the natural home.

## Not verified
- **No live source.** This machine has no container runtime (no Docker/Desktop/Podman/WSL2), so the
  framework was never run against PostgreSQL, Oracle, SQL Server or Elasticsearch. The real-stage
  proof uses D9 mining over synthetic `RawQuery` objects and the SQLite metadata store, plus
  `FakeLLM` for the model-skip criterion. Nothing in the framework touches a network host.
- **No full `mdqm bootstrap run` pass with real stages**: `available_stages()` is empty until the
  D-stage tasks add their objects, so the CLI smoke only covers the empty registry (exit 0, explicit
  message) and `--help`. `--stage/--source/--force` are covered at the `run_pipeline` level.
- **DST edge cases of a quiet window** are F03's tested area and not re-tested here; the pipeline
  only asks `QuietWindow.is_quiet` and computes the next start from the window's own zone.

## Plan issues
- S01's `owns` list is too narrow for its own acceptance text: a ledger needs a migration, and
  "CLI: `mdqm bootstrap run`" needs a command module plus one registration line. Suggest listing
  `src/mdqm/pipeline/cli.py` and a free migration slot in the task, or stating "next free migration".
- `mdqm bootstrap run` is honest but inert until D1..D8 exist. Each D-stage task should add its stage
  object to `available_stages()` (or a registry module), otherwise the command stays a no-op and a
  reader may think the pipeline is broken.
- The task text calls for "abort if source latency rises" but the acceptance bullets do not mention
  it. Implemented and tested (median-of-three ceiling, refusal before the call), but it is a place
  where a future task may want a config knob in `Settings.limits` rather than a `SourceGate` default.
