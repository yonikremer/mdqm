## Summary

Stage D6 (`src/mdqm/pipeline/stages/mutability.py`) classifies every table in a source catalog into the
semantic layer's existing vocabulary (`append_only` / `append_rarely` / `mutable_critical` / `unknown`)
from `pg_stat_user_tables` counters (A04's `mutability_stats()`, reused, not re-implemented), read
**twice** with the lag sampling and old-row checksum work between the two readings, so the recorded
evidence is a delta over a measured window plus the cumulative lifetime counters.

Partitioned parents are rolled up from the partitions the probe reports: a parent's own counters are
zero in `pg_stat_user_tables` however much its partitions hold, which is exactly the trap that would
classify a busy event table as untouched.

Lag is measured, not declared: one bounded sample (`LIMIT`, guarded, `Limits`-capped) of
`ingestion_time - event_time` per table that has both columns, reported as min/p50/p99/max over the
sampled data window, and written as `lag: {min, max, verify: nightly}` with `max` = observed max
× 1.2, rounded up to a whole minute. A later observation above the declared maximum raises
`lag_violated`, keeps the declared bound, and names the column in the stored `lag_unverified` set
(read back with `read_lag_unverified(store, source)`), so C07 can stop deriving on it.

Results go to `generated/mutability_<source>.yaml` through `PipelineContext.write_generated` (round-trip
writer, temp file + atomic replace); `curated/` is never written and still wins on merge.

## Decisions

- **The delta window is short on this world (~0.1s).** The two readings do bracket real work (the lag
  sample and the old-row checksum), but on 5000 rows that work takes a tenth of a second, so the delta
  proves only "nothing changed in that tenth". The classification therefore rests on the **cumulative
  lifetime counters**, which the evidence line states verbatim; the delta is recorded next to it as the
  window evidence the task asks for. On a real primary the same work takes minutes.
- **`updates > 0` is `mutable_critical`**, not `append_rarely`. `n_tup_upd` cannot say whether the update
  hit an old row or the tail, and "we cannot prove it was a new row" has to read as "it may have been an
  old row". That is why `accounts_hist` (updated=5) is critical rather than rarely.
- **A measured positive lag forces `append_rarely`.** `append_only` promises "sealed segments kept until
  `max_ttl`", which holds only if no row can appear inside an already-sealed event-time range. A late row
  can, so the class drops to the one whose policy is tail refresh **plus** the nightly checksum this
  stage also records. `usage_by_load` is partitioned on ingestion time and reports no event/ingestion
  pair, so it stays `append_only`.
- **`status: proposed`, never `approved`.** A measurement is not a human approval (DESIGN section 10),
  and `MutabilityDecl.may_cache` is False while the class is proposed, so nothing measured tonight is
  cached. A human promotes a class by writing `curated/`.
- **The event column is written next to the lag.** `TableSemantics` rejects a `derives_bound_on` whose
  target is not listed under the same table's `time_columns`, so a partial block would make the whole
  generated section unloadable. The generated write is `{event: {role: event_time}, ingestion: {...}}`;
  a curated file that adds `indexed`/`use_by_default` merges on top per key.
- **Partition attribution is exact-or-nothing.** `extract_partitions()` reports partition metadata without
  the table it belongs to, so a set is attributed to a partitioned table only when exactly one catalog
  table's name prefixes every partition name in it. Two candidates or none means no attribution, and a
  partitioned parent with no attribution stays `unknown` with a note (its own counters exclude its
  partitions, so reading them would be the lie this stage exists to avoid).
- **Lag pairs come from the semantic layer when it declares them, else from the catalog**: the partition
  key when it is a single time column, plus a column with a recognised ingestion name
  (`insertion_time`, `ingested_at`, ...). The report says which one answered.
- **Old-row checksum is a cross-run fact.** The stage stores it in `mdqm_meta` under
  `mutability_baseline.<source>` and compares the next pass against it; a change downgrades the table to
  `mutable_critical`. The first pass records a baseline and says "no previous pass" rather than guessing.

## Plan issues

- **A partitioned parent's counters are a trap that every stage reading `mutability_stats()` will hit.**
  `pg_stat_user_tables` reports zero for `usage_events` itself and the real numbers on
  `usage_events_p2025_05`..`_p2025_12`. `mutability_stats()` returns both, but nothing in the model says
  which is a parent, so a consumer that does not roll up (or does not know the hierarchy) will classify a
  busy table as untouched. `extract_partitions()` returns `list[Partitioning]` with **no table name**,
  which forces the name-prefix attribution described above. A `table` field on `Partitioning` (or
  `extract_partitions()` returning pairs) would remove that heuristic. Worth a small task.
- **`ProfilingStage` writes `tables:` as a *list*** (`SourceProfile.model_dump()`), while the semantic
  layer's `tables:` key is a **mapping** of `source.table`. Whichever `generated/*.yaml` merges last wins
  that key whole, so a profile section and a semantics section cannot currently coexist in one semantic
  root. D5's facts are almost certainly meant to live under a different key (or be consumed as a fact
  sheet, not as a layer section) -- this bit me while choosing D6's section shape, and it will bite the
  first person who runs D5 and D6 into the same directory.
- The `pipeline_run` ledger and `StageReport` have no field for "the class I wrote"; D6's counts are
  aggregates (`tables_classified`, `tables_unknown`, `lags_measured`, `lags_violated`,
  `old_row_checks`). Per-table evidence lives in the YAML, which is the durable record.
