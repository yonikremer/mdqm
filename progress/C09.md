## Summary
`src/mdqm/compiler/` turns one validated `QuerySpec` into one `Fragment` for one source: table,
column, measure and join names resolve against the catalog and the semantic layer (`resolve.py`),
measures normalise through the semantic layer's per-source template, time intents become predicates
via C07, partitions are planned via C08 (which may refuse), `LIMIT` is injected from the server cap,
`exec_ts` is substituted via C02, and the result is inspected by the C01 guard before it is returned.
Every statement is built as a sqlglot AST and rendered once; no spec value is ever concatenated into
SQL. Errors are values: `CompiledQuery.error` carries code, problem and an exact `fix`.
Three golden files now pin the compiled statements of the `valid` examples in
`examples/query_specs.json`; five task-E01 questions compile and execute on the DuckDB fake adapter
with the answers E01 derived independently (the 5000 half-up rounding on billing, the `limit_k * 10`
form on erp, a Hebrew label resolved to its source code, a partition window, and the approved
cross-source join with its zero-padded key conversion).

## Decisions
- **Physical table name is the last segment of the semantic key.** A fragment targets one source, so
  the database is chosen by the connection and `crm.customers` is `customers` inside it. This keeps
  one fragment to one connection and needed no rename knob.
- **A fragment may read more than one table.** "Single-source" means one target and one dialect, not
  one table: an approved join's partner appears in the same statement and both keys are listed in
  `Fragment.tables`, so the executor can check reachability. A cross-source join therefore compiles
  and runs wherever both tables are visible (the DuckDB fake holds both).
- **The anchor table must belong to the fragment's source.** A `from` of `crm.customers` with
  `source="billing"` is refused (`INVALID_SPEC`) instead of silently querying the wrong database.
- **`group_by` keys are output columns and come first.** A key that is not also selected must still
  be returned (and `ORDER BY` needs a name for it), so the SELECT list is group keys then select
  items, de-duplicated by output name. This is also the column order E01's answers use.
- **`GROUP BY`/`ORDER BY` repeat the expression, never the alias.** PostgreSQL resolves a `GROUP BY`
  alias against *input* columns first, so an alias there is a correctness hazard; repeating the
  expression is what all four dialects read the same way.
- **A categorical field returns canonical values, a filter uses the source code.** A selected/grouped
  value-mapped column compiles to `CASE col WHEN 'A' THEN 'active' ... END` (actions answer in the
  canonical vocabulary); a filter resolves the label to this table's literal (`status = 'A'`), which
  keeps the predicate index-friendly. An undeclared code falls through to NULL rather than being
  bucketed silently.
- **Ordering/comparison ops on a value-mapped column are refused.** `gt`/`range`/`contains` on
  `customer_status` would order or search stored codes, which is not the business value.
- **`agg` omitted defaults to `sum` and is reported in `applied_fixes`.** The spec says "the measure's
  own default", and the semantic `Measure` model has no default-aggregation field; a silent pick was
  worse than a reported one, and adding the field is another lane's file.
- **`contains` compiles to `POSITION(value IN col) > 0`** (`STRPOS`), so no LIKE metacharacter in a
  filter value needs escaping.
- **Time-bucket `group_by` keys** (`day`/`week`/`month`/`quarter`/`year`) become `DATE_TRUNC` on the
  anchor's event-time column, but only when no table in scope has a column of that name (the catalog
  wins), so a real `month` column is never hijacked.
- **References are qualified as soon as the fragment joins.** With one table a bare column reads
  better; with a join, `customers.status` cannot later become ambiguous.
- **The test semantic layer (`tests/data/semantic/compiler_semantic.yaml`)** mirrors
  `examples/semantic_example.yaml` for everything E01 depends on and adds `usage_units`,
  `event_count` and `billing.accounts.opened_at` (the example layer has no `billing.accounts` entry,
  and the example's trailing-window spec needs an event-time column there).

## Not verified
- **No real PostgreSQL was queried** (no container runtime on this machine). Compilation is proven by
  running the compiled SQL on the DuckDB fake adapter against independently derived E01 answers; the
  Postgres path is exercised only up to rendering and the guard. Concretely unverified on a real
  server: `DECIMAL(38,6)` division semantics inside `AVG`, `DATE_TRUNC('MONTH', timestamptz)`, and
  `POSITION(x IN y)` over a joined table.
- **Session time zone moves a window.** `start_time` is `timestamptz` and the time predicate's
  literal is a naive UTC `TIMESTAMP` (C07 renders it that way), so a source whose session zone is not
  UTC shifts the window by its offset: with the DuckDB session left at `Asia/Jerusalem`, E01's
  October–December count came out 18945 instead of 18946. The end-to-end tests pin the session to UTC
  and say so; making the literal zone-explicit belongs to C07/C02, which already carry a
  `session_time_zone` parameter.

## Plan issues
- **`erp.customers` duplicates are a real gap between E01 and the spec language.** Task E01's erp
  answers dedupe on `(cust_no, status_code, limit_k)` because the world plants six duplicate customer
  records that differ only in `name`; a spec has no "distinct entity" concept, so `AVG(limit_k * 10)`
  over the raw table gives 29719.63 where E01 says 29748.72. The end-to-end erp test uses the same
  deduped view E01's oracle reads, and `test_erp_duplicate_customer_records_are_a_documented_spec_gap`
  asserts the raw mismatch so it cannot disappear. A later task needs an entity/dedupe rule (the
  semantic layer already has `tables.<key>.key`, so the fact is available).
- **Two `Duration` models meet here.** `TableSemantics.default_window` is
  `mdqm.semantic.durations.Duration` (a `timedelta`) while `plan_partitions` expects
  `mdqm.spec.durations.Duration` (a month-aware model). The compiler converts
  (`_spec_duration`), dropping sub-second precision; the two lanes should share one model.
- **`mdqm.results.summary` is flagged by Pyright (not by the project's gates)** for four pyarrow stub
  gaps: `RecordBatchReader.schema` (L263, L265), `pc.count_distinct` (L311), `pc.min_max` (L320).
  `mypy --strict src` is clean and `pytest tests/unit/test_summary.py` passes, so nothing is pending
  there; it is C16's file and outside this task's `owns`, so it was not touched.
- `planner/time.py` leaves its own predicates unqualified while the compiler qualifies its own; with a
  joined query the statement mixes `usage_events.start_time` and `start_time`. Correct today (only one
  table in scope has that column), but the planner should qualify too.
