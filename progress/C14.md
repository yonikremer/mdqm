## Summary

`src/mdqm/cache/segments.py` stores a result as **segments**: one piece per partition (or the part of
one a request asked for), keyed by `(source, table, fragment_hash, version_hash, window)`. A request
is answered by slicing the segments already held and fetching only what is missing, so asking for a
wider range reuses the months inside it instead of refetching them. Rows live in one DuckDB table per
segment (real columns and types), metadata in `_mdqm_segments`; `:memory:` in tests, a file in
production, `memory_limit` and a spill directory set at open, and no DuckDB extension (they need the
internet).

Every served piece is a `SegmentPart` carrying **its own** `fetched_at`, so an answer stitched from an
old month and a fresh one shows both instants instead of one blended staleness. The still-filling
tail is judged against a zero-length span, so the freshness ratio rule degenerates to `min_ttl` (30s)
rather than the hours a month-wide TTL would grant; it is then refreshed by fetching only
`insertion_time >= fetched_at` plus the derived event bound, and merged by unique key. `mutable_critical`
and `unknown` tables never populate the store. Eviction drops segments past `max_ttl`, then the oldest
until the byte budget fits, and reports what it removed.

## Decisions

- **The tail gets `min_ttl`, not the ratio TTL.** Passing a zero-length span to `mdqm.cache.freshness.is_fresh`
  makes the rule `min(max(min_ttl, theta*0), max_ttl) = min_ttl`, so the policy stays in C12's module
  (no second copy) and a still-filling partition is never trusted for hours. Side effect: an immediate
  repeat of a window that includes the tail is a HIT (0 source calls), which is what "a repeated
  identical request is served with zero adapter calls" asks for; moving the injected clock past 30s
  turns it into a tail refresh.
- **The cache builds no SQL.** `fetch_window(Range)` and `fetch_tail(TailFetch)` are the caller's
  closures, so every source call is attributable and `FakeAdapter.calls` proves exactly what ran.
  `TailFetch` carries `since` and the derived `event_bound` (`since - max_lag`) as *values*.
- **Alignment is checked, not trusted.** Each window is re-run through `align_to_partitions` and a
  window that yields more than one piece raises, naming the fix. A segment straddling two partitions
  cannot be judged fresh against either.
- **Tail refresh applies to any stale segment that has a tail policy**, sealed or not: the ingestion-time
  bound is exactly what catches a backdated correction. "Tail" only decides the TTL.
- **`version_hash` lives in the key**, so a semantic bump misses automatically (acceptance 4). Deleting
  the superseded segments is a separate `evict_version(...)` call rather than a side effect of `store`,
  because deleting a row table could break a reader already holding it.
- **`memory_limit` / `spill_dir` are constructor arguments**, not read from `Settings` inside this
  module (see Deviations).
- Merge order: the `_seq` constant (held=0, fetched=1) makes "the newly fetched row wins" deterministic
  without relying on union order. Row *order* is not preserved across a merge, so a caller that promises
  an order sorts the assembled answer (noted in the code).

## Deviations

- **`duckdb` `memory_limit` and the spill directory are passed in, not read from `Settings`.** This
  task's `owns` list is `src/mdqm/cache/segments.py` and `tests/unit/test_segment_cache.py`, and
  `src/mdqm/config/settings.py` has only `PathsSettings.cache_dir` — no `memory_limit` key. Adding one
  meant editing another lane's config model, so the store takes both as explicit arguments (with the
  generic defaults `512MB` and "no spill dir") and the caller passes `Settings.paths.cache_dir`. Recorded
  as a plan issue below.
- `TailPolicy.max_lag` is optional; without it no derived event bound is produced, so the caller filters
  ingestion time only, which does not prune. That is the caller's trade-off and is documented in place.

## Not verified

- No real PostgreSQL/Oracle/SQL Server/Elasticsearch: this machine has no container runtime (no Docker,
  Podman or WSL2). Everything ran against F05's in-process DuckDB adapter, which is the only "real
  adapter" definition the project has. C14's acceptance criteria are all expressible against it.
- DuckDB file-backed behaviour was verified by reopening the same file in a fresh `SegmentCache`
  (`test_a_file_backed_store_survives_a_reopen`), not by a concurrent multi-process deployment.
- Clock skew between server and source is assumed small: `since` is *our* `fetched_at`, so a source
  clock ahead of ours could hide rows inserted at exactly that instant. The dedupe-by-key makes an
  overlapping `>=` safe, but it cannot compensate for skew. Not measurable here.
