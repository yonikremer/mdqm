## Summary

`src/mdqm/testing/loaders/postgres.py` builds the world in-process
(`mdqm.testing.world.build_world`) and materialises it in the three compose databases:
`crm.customers`, `billing.{accounts, accounts_hash, accounts_hist, status_lookup,
usage_events, usage_by_load, accounts_current}` and `erp.customers`. DDL is
drop/create-per-table, all rows go in with `COPY ... FROM STDIN`, then `ANALYZE` and the
read-only grants run in each database. `python -m mdqm.testing.loaders.postgres [--small]`
is the CLI; it reads `MDQM_PG_PASSWORD` / `MDQM_RO_PASSWORD` / `MDQM_PG_PORT` from the
nearest dotenv file (walking up from the working directory) or from the environment.

Shape choices that the acceptance criteria depend on:
* `usage_events` is RANGE-partitioned on `start_time` with **14** pre-created monthly
  partitions ending at the anchor month, an index on `start_time`, and **no** index on
  `insertion_time`;
* `usage_by_load` is RANGE-partitioned on `insertion_time` with **16** partitions (two past
  the anchor, because ingestion lag may cross it);
* `accounts_hash` is HASH-partitioned on `client_no` into 4 partitions;
* `erp.customers` has no primary key, so the world's duplicate rows survive;
* NULL raw limits, orphan `client_no`s and every planted exception are copied verbatim.

## Decisions

1. **`usage_events` stops at the anchor month (`forward=0`), `usage_by_load` does not.**
   An open-ended lower bound cannot prune a partition that lies entirely *after* the bound,
   so extra future partitions on `usage_events` were scanned for nothing (measured: 3
   partitions instead of 1). `usage_by_load` keeps two forward months because ingestion time
   genuinely runs past the anchor (lag <= `max_lag_seconds` = 6 h).
2. **The pruning test is anchored to the world, not to `now()`.** The machine clock
   (2026-11-27) is past the whole event window (2025-05-01..2026-01-01), so a literal
   `start_time >= now() - 30 days` prunes to **zero** partitions and would satisfy "<= 2
   partitions" vacuously. The test uses the window's last 30 days
   (`ANCHOR - 30 days` = 2025-12-02), which touches exactly **1** event-time partition, and
   the identical bound on `insertion_time`, which touches **all 14**.
3. **Two read-only layers are asserted, not one.** With the role default the failure is
   SQLSTATE 25006 (read-only transaction); after `SET default_transaction_read_only = off`
   it is still refused with 42501 (missing privilege / not owner / no CREATE on schema
   public). Asserting both proves the setting and the grant, not just whichever fired first.
4. **Partition key in the primary key.** `usage_events` PK is `(event_id, start_time)` —
   PostgreSQL rejects a PK that omits the partition key. `usage_by_load` is
   `(event_id, insertion_time)` for the same reason.
5. **`accounts_current` view** (DISTINCT ON latest revision) is shipped with
   `accounts_hist` so the "frequently updated table" has the shape its consumers will want.
   It is dropped and recreated with the rest, keeping the loader idempotent.
6. **Dotenv discovery walks up from the working directory.** A git worktree under
   `.worktrees/<task>` therefore reuses the checkout's credentials file instead of needing
   its own copy; nothing is hard-coded and no secret is read by anything but Python.

  customer / 50k event world; that is how the acceptance output below was produced last.
