## Summary
Built the human-approval gate in `src/mdqm/review/queue.py` over the metadata SQLite store
(migration `0004_review.sql`, next free number). A proposal carries a content-hash id, kind, section,
item key, optional field path, patch, evidence, confidence and status (pending/approved/rejected/
never_ask) with who/when. Only `ReviewQueue.approve` writes `curated/*.yaml`: it merges the patch with
`ruamel` round-trip (comments and key order elsewhere in the file survive), adds provenance
(approved_by/approved_at) or `status: approved` for mutability, then reloads the layer through the C04
loader and rolls back if the result would not load. Rejections are remembered: the same fact with the
same evidence is suppressed, with changed evidence it resurfaces (evidence_hash comparison). Approved
and rejected decisions also append to the H02 hash-chained audit log. `export_patch` renders the same
merge as a unified diff for the PR flow, and `mdqm review list|approve|reject|export-patch` exposes it.

## Decisions
- **Explicit `key` + `field` instead of one dotted `target`.** A table key like `billing.usage_events`
  contains a dot of its own, so splitting a dotted path can never recover it (found by the mutability
  test). `key` names the item verbatim, `field` is the dotted path inside it; `target` is a derived,
  human-readable property. The id hashes kind+section+key+field+patch.
- **Evidence is not part of the id.** Otherwise a rerun with new evidence would open a *second*
  question about one fact instead of resurfacing the existing one; the resurface rule needs a stable
  row. `evidence_hash` (order-insensitive) is stored separately and compared.
- **`collection` flag for list sections.** `approved_joins` is a list matched by `name`, not a mapping
  to merge; the flag keeps that explicit rather than guessing from the section name.
- **Approval validates by reloading the whole layer** and rolls back on failure (deleting a file it
  just created, restoring the previous text otherwise). A semantic layer that cannot load is worse
  than a proposal that stays pending. Verified for both a new file and an existing file.
- **A failed approval is not audited.** Only a real decision is; an audit row saying "approved" for a
  refusal would be a lie.
- **Audit records the proposal id, not the patch.** `AuditEntry` deliberately holds no payload, so
  the id goes in `version_hash`; an audit reader follows it back to the row.
- **CLI accepts a unique id prefix** (12 chars, as the digest prints) and refuses an ambiguous one,
  because typing 64 hex characters is not a realistic human action.
- **`never_ask`** is a fourth status beyond the three in the task text: a rejection the operator does
  not want to revisit even when evidence changes (the task's "never ask" case). It suppresses
  unconditionally; `rejected` suppresses only while the evidence is unchanged.
- Bulk threshold defaults to 0.9 confidence; `questions()` groups those into one `Question` so a
  digest asks once, which is what "counts as one question" means for a reader's attention.
