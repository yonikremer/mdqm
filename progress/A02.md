## Summary

`src/mdqm/adapters/postgresql.py` is the PostgreSQL `SourceAdapter`: a lazily opened
`psycopg_pool.ConnectionPool` whose every connection is configured
`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`, a session `statement_timeout`,
`idle_in_transaction_session_timeout`, `TimeZone = 'UTC'` and `application_name = mdqm:<user>`;
`extract_catalog` (tables, columns with native + normalised types, PK, FK, indexes with the
key/INCLUDE split, comments, `reltuples` estimates, partitioned parents marked
`kind=partitioned_table`); `execute` streaming a **server-side cursor** into `pyarrow.RecordBatch`
with `max_rows`/`max_bytes`/`timeout_s` enforced by the adapter; `cancel` via
`Connection.cancel()` (idempotent, safe from another thread); and `extract_partitions` from
`pg_partitioned_table`/`pg_inherits`/`pg_get_partkeydef`. Registered as the `postgresql` entry point
in the `mdqm.adapters` group.

## Decisions

- **`SET` takes no bind parameter.** The first attempt used `SET statement_timeout = %s`; PostgreSQL
  answers `syntax error at or near "$1"` and the pool then refuses every connection. The deadline is
  now composed through `psycopg.sql` (`sql.SQL(...).format(sql.Literal(ms))`), never concatenated,
  and the value is an `int` by construction.
- **`SET LOCAL statement_timeout` runs on a plain cursor, the query on a named one.** psycopg wraps
  a named cursor's `execute` in `DECLARE`, so `SET LOCAL` sent there becomes
  `DECLARE "c" CURSOR FOR SET ...` — a syntax error.
- **`numeric` becomes `pa.decimal128(38, 9)`.** Arrow decimals are fixed-scale and PostgreSQL's
  `numeric` is not, so a value with more than 9 fractional digits raises `ArrowInvalid` instead of
  being silently rounded. Losing a digit of money quietly is worse than a loud failure. A
  `numeric` column whose scale exceeds this would need a per-column precision captured in the
  catalog — recorded here rather than guessed at.
- **Unknown types are carried as text**, not dropped: `jsonb`, `uuid`, arrays, ranges and intervals
  go through one `_as_text` that dumps JSON in a stable key order. A column the adapter cannot type
  is still readable by an agent.
- **Partition children are not catalog tables.** They inherit the parent's PK and indexes and would
  add a monthly copy of the same table to everything an agent sees. The parent is marked
  `partitioned_table` and `extract_partitions` reports the children.
- **`explain_plan`, `query_store`, `mutability_counters` are reported *unprobed* (`None`) with a
  detail naming task A03/A04**, not `unsupported`. PostgreSQL can do all three; saying "this source
  cannot" would make the capability report repeat a lie.
- **`cancel()` sends the cancel request only** and leaves cursor/connection release to `close()`, so
  cancelling from another thread cannot close the socket under an in-flight `FETCH`.
- Unknown `options` keys are logged by name (not fatal): another lane may add one, and a typo should
  be visible rather than swallowed.

## Deviations

- `Partitioning` carries no table name, so `extract_partitions() -> list[Partitioning]` cannot tell a
  caller which table each entry belongs to (`mdqm.pipeline.stages.drift` already expects
  `Mapping[str, Partitioning]`). `tests/integration/test_pg_adapter.py` selects the event-time
  partition set by its key `("start_time",)`, which is unique in the world. **Not fixed here**:
  `src/mdqm/models/partitioning.py` is not in this task's `owns` list, and A03 owns the definitive
  partition work. See "Plan issues".

## Dependencies

None new. `psycopg` 3.3 and `psycopg-pool` 3.3 were already the `pg` extra (AGENTS.md section 3);
`psycopg-pool` ships `py.typed`, so `mypy --strict` checks this module without an override.

## Not verified

- Oracle, SQL Server and Elasticsearch: nothing here was exercised against them.
- A `numeric` column with more than 9 fractional digits (see Decisions): it raises, and that path is
  not covered by the shipped world.
- `fragment.params` with psycopg named placeholders is supported but untested end to end: the
  compiler inlines literals, so no lane produces a parameterised fragment yet.
- Multi-column RANGE bounds (`FOR VALUES FROM (1, 'x') TO (...)`) parse to a bound with no
  datetimes rather than being guessed. No such table exists in the world.

## Plan issues

- **`Partitioning` has no `table` field.** `SourceAdapter.extract_partitions` returns
  `list[Partitioning]` while `DriftStage.PartitionReader` is `Callable[[str], Mapping[str,
  Partitioning]]` — whoever wires the two has to invent the mapping. A03 (or a small model change)
  should add `table: str | None` before the drift stage consumes a real adapter.
- **`SET`-based session settings cannot use bind parameters**, so every adapter that configures its
  session needs `psycopg.sql` composition. Worth a line in DESIGN's adapter section for the Oracle
  and SQL Server adapters (which have the same constraint).
- A02's acceptance ("catalog of billing lists usage_events with indexes") and A03's ("partition
  metadata") overlap on `pg_inherits`. `extract_partitions` here is the minimum that proves the
  14-partition acceptance; A03 should supersede it (bounds parsing with granularity, expression
  keys) rather than duplicate it.

Note on the DML refusal: a server-side cursor cannot carry DML at all, so PostgreSQL answers a plain
`DELETE` with `42601` from its own parser. The read-only-transaction layer is therefore proved
separately, with `SELECT nextval(...)` — a cursor-able query that writes permanently, where
`mdqm_ro` was granted `USAGE` on the sequence first (otherwise the answer would be
`42501 permission denied`, which proves nothing about the transaction).
