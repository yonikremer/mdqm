## Summary
`src/mdqm/store/db.py` is the metadata SQLite layer: stdlib `sqlite3`, WAL, one connection per thread,
one in-process writer lock, and numbered forward-only SQL migrations under `src/mdqm/store/migrations/`
recorded in `schema_migrations`. `Store.initialize()` is idempotent (a second start reads only), each
migration runs in its own `BEGIN IMMEDIATE` transaction so a failure rolls back completely and leaves
the previous version intact, and a DB written by a newer build is refused instead of downgraded.
`0001_initial.sql` adds `mdqm_meta(key, value, updated_at)`; later tasks add their tables as `0002+`.
FTS5 is probed, never assumed: `check_fts5()` creates a `temp` FTS5 table, indexes one English and one
Hebrew row, searches and drops it; absence comes back as `Fts5Status(available=False, detail=...)`
(with `.capability()` in the `Capability` shape the capability map stores) instead of an exception, and
`require_fts5()` is the one place that fails loudly, naming `sqlite3 <version> in Python <version>` and
the interpreter path.

## Decisions
- **Migrations are plain `.sql` files** in the package (shipped with the wheel), loaded by
  `load_migrations()`; a `*.sql` file whose name is not `NNNN_name.sql` raises instead of being silently
  skipped (principle 10), and two files with one version raise too.
- **Statements are split with `sqlite3.complete_statement`, not `Connection.executescript`.** On Python
  3.12 `executescript` commits before running the script, which would break the "failed migration rolls
  back" guarantee. Consequence, documented in the module docstring: one statement per line, each ending
  with `;`.
- **`schema_migrations` is created by the store, not by a migration** (it must exist before the first
  one), with `CREATE TABLE IF NOT EXISTS`.
- **Downgrade refused**: `initialize()` raises `StoreError` when the DB version is above this build's
  target, because running an old build against a newer schema would drop columns silently.
- **`writing()` is the write path** (lock + immediate transaction) and is deliberately not re-entrant;
  task H02/H03 should use it instead of touching connections directly.
- **No injected `Clock`**: `applied_at` is `datetime.now(UTC).isoformat()` and no test asserts on it, so
  nothing sleeps or becomes flaky.
- The writer lock covers our own threads; two *processes* are handled by SQLite's own
  `BEGIN IMMEDIATE` + 5 s `busy_timeout`, and a pathological cross-process race would fail loudly on the
  `schema_migrations` primary key rather than half-apply. DESIGN section 14 says single instance.
- `Store` does not read `Settings`: the caller passes `Settings.paths.metadata_db` (no global state).

## Not verified
- Running against a Python build whose SQLite really lacks FTS5. There is none on this machine, so the
  absence path is covered by a stub connection that raises `sqlite3.OperationalError("no such module:
  fts5")` (exactly what such a build answers) plus the honest branch inside the real smoke test, which
  asserts "reported, not raised" if the build ever turns out to lack FTS5.
- Multi-process concurrent migration (no second process is started in a unit test); single-process
  instance is the documented deployment.

## Plan issues
- H01's acceptance text says "if missing, fail with a clear error naming the Python build", which reads as
  if the whole store crashed without FTS5. Taken literally that would break SQLite's own use for history
  and audit, which do not need FTS. Implemented as: probe reports unsupported, `require_fts5()` raises
  only where FTS is genuinely required (H03 history search, H04 Context Pack). Both readings are
  satisfied, the conservative one is the one that keeps the server running.
- The shipped migrations directory must be included in the wheel; hatchling's default file selection
  includes package data under `src/mdqm`, so no `pyproject.toml` change was needed. Worth a packaging
  smoke test when the image task lands (nothing today builds a wheel in CI).
