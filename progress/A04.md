## Summary

`PostgresAdapter.mine_queries()` reads `pg_stat_statements` from the live server and yields one
`RawQuery` per statement (calls, total/mean execution time, rows, user, text). The logic lives in the
owning module `src/mdqm/adapters/postgresql_stats.py`; `postgresql.py` keeps only the two thin
methods and the probe wiring. The probe now claims `query_store` only when the extension exists
*and* the role may select from it, and claims `mutability_counters` from `pg_stat_user_tables`
(which is why `run_conformance` in A02's test now really exercises `mine_queries`).

Because the view stores *cumulative* counters, the adapter hands over **deltas** against its previous
reading (the first call is the baseline) — stage D9 sums what it is handed, so the same totals twice
would count one execution twice. `DECLARE "c1" CURSOR FOR <query>` rows are unwrapped to the
statement, so a read through our own server-side cursor aggregates with the same statement run
directly; session plumbing (`BEGIN`/`SET`/`FETCH`/…) and masked text are dropped.

## Decisions

- **Deltas, not totals.** `pg_stat_statements` counters are cumulative since
  `pg_stat_statements_reset()`. The watermark is the previous reading of the same adapter instance
  (in-process, not persisted): a restarted process takes one larger baseline, never a double count.
  A counter that goes backwards (a reset) is detected and the baseline restarted.
- **Grouped by statement text, not `queryid`.** The view groups by `queryid` *and* raw text, so one
  statement can arrive as several rows (every `DECLARE "<cursor name>"` is its own row).
  `statements()` sums them per text, otherwise "run the same query twice" reported two rows of one
  call each.
- **`DECLARE ... CURSOR FOR <query>` is unwrapped.** Otherwise every read through our own
  server-side cursor mines as an unparseable `DECLARE`, and mining would have nothing to rank.
- **Plumbing is dropped** (`BEGIN`, `COMMIT`, `SET`, `FETCH`, `PREPARE`, …): `FETCH FORWARD 1000`
  had 168 112 calls on this server and would swamp any ranking with our own cursor traffic.
- **`since` cannot filter a statement** on this extension: 1.10 keeps totals, no per-statement
  first/last seen (`stats_since`/`minmax_stats_since` arrive in 1.11/PostgreSQL 17). So
  `RawQuery.last_seen` is `None` and `since` is only logged when it falls outside the counters'
  own window; the capability detail says "no per-statement first/last seen". The alternative —
  inventing a timestamp — would be a lie in the evidence the pipeline ranks on.
- **`GRANT pg_read_all_stats TO mdqm_ro`** added to `docker/pg/init/01-init.sh`. Without it the view
  masks every other role's text as `<insufficient privilege>`; mining would then return only our own
  reads and look calm about it, which the task forbids. Read-only by nature: it exposes statistics,
  not data and not a write. `pg_stat_statements.track=all` (already in `docker-compose.yml`) is what
  makes nested statements visible; nothing had to change there.

## Not verified

- **Nested statements** (`pg_stat_statements.track=all`): the setting is on in `docker-compose.yml`
  and the view reports `track = all`, but no test executes a statement inside a PL/pgSQL function,
  so `toplevel = false` rows are not exercised. They will arrive as ordinary rows (the miner does not
  filter on `toplevel`), and the same statement seen both ways is summed, not duplicated.
- **Reset behaviour** (`pg_stat_statements_reset()` mid-run, the backwards-counter path) is
  implemented and logged but not tested against the live server: resetting the shared view would
  disturb every other integration test on this cluster.
- **`total_time`** (PostgreSQL ≤ 12 column name) is detected from `information_schema` but never
  seen on this server (16.16 uses `total_exec_time`).
- Extension-missing case is tested by creating and dropping a scratch database
  (`mdqm_a04_noext`) on the same server, which is the real "not created" condition; a server started
  *without* `shared_preload_libraries` would additionally refuse `CREATE EXTENSION`, and the probe's
  detail names that requirement.

## Follow-up after the merge (same branch, second commit)

- `mine_queries()` is no longer a generator that opens the connection lazily: it returns
  `iter(mined)`, so `NotSupported` is raised by the **call**, not on first iteration. A caller that
  only takes the iterator (or logs the failure) no longer sees "supported" and then nothing.
- `src/mdqm/planner/partitions.py` (C08's file): the two `sqlglot.errors` pyright findings were
  fixed on `main` in `a605b63` (`planner: import sqlglot.errors explicitly and refuse an empty
  partition key`), which also handles the `partitioning.key[0]` narrowing, so this branch does not
  touch that file at all. `main` had moved under the branch; the duplicate fix was dropped in the
  rebase rather than merged twice.

- `tests/unit/test_registry.py` (registry lane, not in `owns`, smallest possible edit): `main` was
  red before this branch touched anything. The test asserted `AdapterRegistry().discover() == ()`
  with the comment "no adapter distribution is installed for mdqm itself", but `pyproject.toml` now
  declares `[project.entry-points."mdqm.adapters"]` (postgresql, openapi) and the editable install
  exposes them, so discovery returns them and the assertion fails on `main` itself (proved by running
  the single test in the main checkout). The test now compares discovery against exactly that entry
  point group -- still proving the group is what discovery reads, and green whether or not the
  distribution is installed. Without this, `scripts/integrate.py` cannot integrate any task.
