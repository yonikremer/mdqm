## Summary
`src/mdqm/eval/harness.py` answers every E01 question twice -- the curated **spec** path (compile + run
against the real source) and E01's **oracle** SQL (executed directly) -- and scores both against the
ground truth, printing a table and a machine-readable report. The model leg deliberately lives in
`scripts/bench_glm.py` so a harness run is deterministic and needs no endpoint.

## What it found (the reason this is `partial`, not `done`)
Two assumptions in the E01 fixture disagree with the D03 database layout. Neither is a harness bug;
both are real inconsistencies in the repo that the harness exposed:

1. **`erp.customers` column name.** The live table has `cust_no, name, status, limit_k`; E01's oracle
   SQL and `examples/semantic_example.yaml`'s value map both say `status_code`. The oracle leg for the
   two erp questions therefore fails with `UndefinedColumn`, and the spec leg answers through a
   column the curated layer names differently.
2. **Oracle SQL is schema-qualified by source.** E01 writes `billing.usage_events`,
   `crm.customers` -- i.e. it assumes one database with one schema per source. D03 loads three
   **separate databases** whose tables live in `public`, so the oracle leg fails with
   `UndefinedTable`. The product's own layer maps source -> database at the connection, not in SQL.

Both are fixable (rename the erp column in the loader, or rewrite the oracle SQL per database), and
until one of them is chosen the harness cannot report a truthful 15/15.

## Evidence
- Each verdict prints `spec` and `oracle` plus the failure detail; e.g.
  `customers_by_region_crm rows PASS ERROR UndefinedTable: relation "crm.customers" does not exist`.
- `churned_customers_hebrew` and `customers_by_region_crm` pass on the **spec** path, which shows the
  pipeline itself is answering the question while the oracle leg is the one that cannot run.

## Decisions
- The harness reuses `scripts/bench_glm.py`'s scorer instead of writing a second comparison: one
  definition of "matches ground truth" for both the offline and the model benchmark.
- A failing leg is reported per question, never swallowed: `ERROR` carries the driver's message.

## Update after the layout fixes (still `partial`)
Two of the three blockers above are gone: the erp column is now `status_code` everywhere, and the
oracle leg no longer runs against PostgreSQL -- E01's `oracle_sql` is DuckDB-flavoured (integer
division with `//`, one schema per source), so it now runs in an in-process DuckDB holding the same
world. That leg passes for 9 of 15 questions.

What the harness itself still gets wrong, found by running it:
1. **Adapter streams are not closed** after draining. The pool then times out after four questions
   (`PoolTimeout: couldn't get a connection after 30.00 sec`) and three questions report `ERROR`
   instead of an answer. This is a defect in `run_spec_path`, not in the product.
2. **The spec leg disagrees with the oracle on four single-table averages** while the *product* path
   (proven by `tests/integration/test_acceptance_e2e.py` and by the GLM benchmark at 15/15) agrees
   with the ground truth. So the harness's spec leg is not doing what `query` does -- it compiles and
   executes without the value-map/value-map post-processing the tool applies.

Until those two are fixed the harness cannot be trusted as a verdict, which is why this row stays
`partial`: a harness that reports `FAIL` where the product is right is worse than no harness.

## Second update: the spec leg now goes through the product (13/15), the oracle fixture is the gap
The harness no longer compiles and executes on its own -- it calls `scripts/mdqm_call.py`, i.e. the
same client, transport and tool envelope an agent uses. That closed the false `FAIL`s immediately:

    avg_limit_by_status_crm / billing / erp, avg_limit_by_region_billing, sum_limit_by_status_erp,
    events_count_window, new_since_resync, units_new_since, known_as_of_snapshot,
    churned_customers_hebrew, customers_by_region_crm, top_clients_by_usage_december   -> PASS (13/15)

The one remaining spec `FAIL` is `usage_units_by_status_window` (the joined aggregate); `delete_*` is
`SKIP` because the tool has no way to express a write (see E03).

**The oracle leg is the part that is now suspect, not the product.** In DuckDB over the same world it
returns 18945 where E01 says 18946 for `events_count_window`, and 2405870 vs 2401918 for
`units_new_since` -- while the *product* returns E01's number for both. So the in-memory fixture this
harness builds is not the dataset E01's answers were computed from (a correction/backdated row is the
likely difference). Until that fixture matches, the oracle leg cannot be a verdict, and the row stays
`partial`.

Honest summary: **the product's answers agree with E01 on 13 of 15 questions through the real tools**;
the harness's own oracle fixture disagrees with E01 on 6, which is a defect in the harness.
