## Summary
`src/mdqm/pipeline/stages/catalog.py` is stage D1+D2: it reads each configured source's catalog and
partition metadata (A02/A03) and writes `generated/catalog.yaml` -- tables, columns with native and
normalised types, primary keys, indexes, and the partition scheme with the server's own bounds.
Registered with the bootstrap CLI, which now builds adapters from settings and hands them to the
stage, so `mdqm bootstrap run` does real work instead of reporting "no stage is registered".

What it deliberately does **not** write: time-column roles (`event_time` vs `ingestion_time`),
mutability, measures, value maps. Those are conclusions -- measured by S05 or proposed and approved
through the review queue -- and a guess written as a generated fact would be indistinguishable from
an approved one.

## Evidence (executed, not reasoned)
- Live run against `billing`: 9 tables, 82 columns, 3 partitioned tables, **34 partitions** written;
  `usage_events` carries `start_time` / `month` / 14 bounds, `usage_by_load` 16 (on `insertion_time`),
  `accounts_hash` 4 (hash on `client_no`).
- The generated file loads back through `mdqm.semantic.loader.load` and reports the same partitioning
  -- a generated file the loader rejects would be a file nobody can use.
- Two reads of the same catalog produce the same input hash, which is what lets the runner skip an
  unchanged schema.

## Decisions
- **One section, not one file per source**: the loader merges every `generated/*.yaml` into a single
  document, so per-source files would collide on the same top-level `tables` key.
- **The semantic namespace is the source name**, not the database schema: `billing.usage_events`, not
  `public.usage_events`. Two sources usually both live in a `public` schema, and the curated layer and
  the query specs already use the source-prefixed keys.
- **Partition ownership comes from the bound name.** `Partitioning` (F02) carries no table name, so the
  stage maps `usage_events_p2025_12` -> `usage_events` by longest matching table name (so
  `customers_hist` is never claimed by `customers`). An ambiguous or unmatched bound is dropped, never
  attached to a neighbour: a wrong partition key is worse than a missing one.
- Stage typed against a narrow `CatalogReader` protocol rather than the full `SourceAdapter`, so a test
  double does not have to implement `execute` to prove what the stage writes.

## Deviations
The backlog names this "stages D1+D2"; it is one stage object covering both, because the partitioning
is nested inside each table entry and cannot be written by two independent stages without one
overwriting the other.
