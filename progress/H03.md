## Summary

Query history in `src/mdqm/store/history.py` over migration `0003_history.sql`: one row per run holding the
user, tool, mode, `exec_ts`, the validated spec, the original SQL and the SQL with `exec_ts` frozen in, the
per-source fragments, `applied_fixes`, the plan summary, cache/freshness info, duration, the agent-facing
error, and a redaction count. `rerun(id, mode='frozen'|'relative')` returns a `RerunPlan` whose fragments are
the payloads a source will receive: a frozen re-run reproduces the run byte for byte (same window, same
`exec_ts`) even after the clock moved; a relative re-run re-derives every payload from the original at a fresh
`exec_ts`, so the window moves and *only the timestamps change*. `search(text)` is FTS5 over a normalised
text column (Hebrew with or without niqqud, English, either case) with a `LIKE` fallback; `purge()` removes
only rows older than the retention window.

## Decisions

1. **Two spellings of every payload.** A row stores both the original (`now() - interval '7 days'`,
   ES `now-7d/d`) and the executed, substituted payload. Storing only the executed one would make a relative
   re-run hand back the *old* window under a *new* `exec_ts` — the silent change this task exists to prevent.
2. **Reproducibility is verified at write time, not trusted.** `record()` refuses a row whose declared
   original does not re-substitute byte-identically at the stored `exec_ts`, whose dialect has no defined
   substitution, or whose payload still holds a now-like value with no original to re-derive from. Refusing
   to store beats storing a row a re-run would answer wrongly.
3. **Honest limit, stated in the module docstring:** the check reads text. A caller that hands over an
   already-substituted payload *and omits the original* is indistinguishable from a query that never had a
   now-like value. The pipeline must record both; every original that is recorded is verified.
4. **The FTS index is created lazily, not in the migration.** `CREATE VIRTUAL TABLE ... USING fts5` fails on a
   Python build without FTS5, and a failing migration would take the audit log down with it. `HistoryStore`
   creates and backfills the index inside its writer transaction and falls back to an equivalent `LIKE` scan
   when the capability probe says FTS5 is missing (principle 1). Both paths are tested.
5. **Credentials: redact, count, and refuse to re-run.** Every text column (spec, SQL, fragments, fixes, plan,
   cache, error) is scrubbed before it is written and the search text is built from the scrubbed values, so no
   index entry holds a secret either. The shape list is the audit log's (`mdqm.store.audit._SECRET_SHAPES`),
   imported rather than copied, and *extended* here with value-consuming shapes (`password=...` and whole PEM
   blocks): an audit field is refused outright, whereas free text is kept, and the audit pattern alone would
   redact the key and leave the value standing. Over-redaction is reported in `redactions`, and `rerun`
   refuses a redacted row instead of returning a fragment that differs from what ran.
6. **Retention keyed on `created_at`, not `exec_ts`**: a frozen re-run of an old window stored today is kept
   for the same year as any other run. `DEFAULT_RETENTION_DAYS` is reused from the audit module (one "one
   year", DESIGN section 13).
7. **No window is stored separately.** The window *is* the predicates in the fragments, and the fragments are
   what a re-run executes, so the planner (`mdqm/planner/time.py`) stays the single owner of that rule.
8. **`rerun` accepts `mode='frozen'`/`'relative'` as text and coerces** to `ExecTsMode`: `resolve_exec_ts`
   branches on identity, so passing a raw string would silently give a relative re-run for a frozen request.
9. **A run with no spec, no SQL and no fragments is refused by the model**, not stored as a memory of nothing.

## Deviations

- `mdqm history` CLI subcommand and the MCP `history` tool are **not** wired: `src/mdqm/cli.py` and
  `src/mdqm/server/tools.py` are outside this task's `owns` list, and there is no pipeline yet to produce a
  `HistoryEntry` (it needs the compiler's fragments). `HistoryStore.recent()`/`search()` are the API they will
  call. Worth a follow-up task once H03's consumer exists.
- `docs/DESIGN.md` section 13 already describes exactly this (spec or original SQL, frozen-`exec_ts` SQL,
  per-source SQL, fixes, errors, partitions, cache, `fetched_at`, one-year retention, frozen vs relative
  re-run), so the design did not change and was left untouched.

## Dependencies

None added. Uses stdlib `sqlite3`/`json`/`re`, plus already-present `pydantic`, `sqlglot` and the existing
`mdqm.sql.exec_ts`, `mdqm.spec`, `mdqm.semantic.text` modules.
