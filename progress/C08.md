## Summary

`src/mdqm/planner/partitions.py` is the pure static partition planner: given one table's
`Partitioning` metadata and the sqlglot predicates of a fragment, it decides whether the scan is
pruned and what it would cost.

- **Missing key filter** -> `PARTITION_SCAN_ALL` with a `fix` naming the spec `time` field and the
  key column, plus `partitions_if_fixed` computed from the declared bounds (e.g. `"2 of 8"`). When
  the table sets `require_key_filter: false` *and* declares a `default_window`, the window
  `[exec_ts - default_window, exec_ts)` is injected and reported instead (`default_window_applied`
  note + `applied_fixes`, and the estimate reflects it). A refused plan provably calls no source.
- **Function or cast on the key** (`CAST(x AS DATE)`, `TRUNC(x)`, `date_trunc('unit', x)`, nested
  floors) is turned into a range on the raw column. The original predicate is **kept**, so the
  added range is implied by it and the answer cannot change; that is what makes the rewrite
  provably safe rather than "probably equivalent".
- **Estimate and cap**: the partition and row counts come from the declared bounds and
  `row_estimate`s alone; over `max_partitions` the plan refuses with `COST_TOO_HIGH` and the count.
- **List / hash / expression / none**: list matches declared `values` (ANDed equalities intersect,
  so a contradictory filter estimates 0); hash needs a filter on the key itself and reports the
  value count as an upper bound; an expression key prunes only through its declared expression or
  its own column, anything else gets `needs_human_approval`; `none` plans nothing.
- `align_to_partitions(window, granularity)` splits a window at partition boundaries (days, ISO
  weeks, months, quarters, years) into consecutive half-open pieces for the cache, covering exactly
  the window asked for.

## Decisions

- **The rewrite adds an implied range and keeps the original predicate.** Replacing it would need a
  proof per dialect (rounding of `CAST`, non-aligned `date_trunc` constants, timestamp resolution
  for an inclusive `<=`). Adding an implied predicate is correct by construction and still lets the
  source prune, and `tests/unit/test_partition_planner.py` compares row sets before/after on the
  D02 world in DuckDB.
- **Upper bounds move out to the next partition boundary; lower bounds stay where they are.**
  `date_trunc('month', x) < '2026-11-15'` implies `x < '2026-12-01'`, not `x < '2026-11-15'`; the
  reverse holds for `>=`. This is the one direction that can silently lose rows, so it is the one
  direction handled explicitly (the test table names the case).
- **An inclusive upper bound stays inclusive.** `BETWEEN`, `<=` and `=` keep an `<=` in the derived
  predicate instead of inventing a `+1µs` exclusive bound: the derived predicate must be *exactly*
  implied, and timestamp resolution differs between sources (Postgres µs, Oracle ns).
- **`exec_ts` is injected** and required to be aware UTC; a naive one raises `ValueError` (an
  internal bug), never an `ErrorResponse` (which is reserved for what an agent can fix).
- **A filter that exists but cannot be proved prunable is not an error.** It returns
  `needs_human_approval` (or `estimate_unproven` for hash/multi-column) with the full declared count
  as the estimate, and the `max_partitions` cap decides. Blocking would tell an agent that already
  filtered the key to "add a filter on the key", which is not a fix it can act on.
- **List/hash values are matched exactly** (string form of the literal against the declared
  `values`). A wrapped key (`lower(region) = 'x'`) never matches: it is not a partition value.
- **`estimate_partition_scan(partitioning, window)` is public** because the hypothesis property
  ("adding a key filter never increases the estimate") needs to compare two windows directly, and
  the explain gate (C09/E-lane) can reuse it without re-deriving it.
- **Multi-column keys**: a filter is required on every key column, but the count is reported as the
  full declared total (`estimate_unproven`), because one-dimensional bounds cannot say how many
  multi-dimensional partitions are touched. A default window is never injected for them.

## Plan issues

- The task says the planner gets "the predicates of a fragment", but no compiler exists yet (C09),
  so no caller passes them. The signature is therefore `Sequence[exp.Expression]` (the same currency
  `TimePlan.predicates` uses), which is what C09 will have in hand after ANDing the time plan's
  predicates in; nothing in this module reads a spec or a clock.
- `Limits.max_partitions` (F02) and `Settings.max_partitions_scanned` (C15) are two knobs for the
  same decision; this planner takes one `max_partitions: int | None` and leaves the precedence
  (limits over settings) to the caller rather than guessing it here.
