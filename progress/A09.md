## Summary

`src/mdqm/adapters/elastic.py`: a read-only Elasticsearch `SourceAdapter` (`kind="elastic"`,
`dialect()=="dsl"`) over plain `httpx`. It probes the cluster (version, ES|QL `_query`, aggregation
availability), reports capabilities only under `OPTIONAL_METHODS` names, turns each **alias** into
one table with the monthly indices as its partitions, and executes a fragment's Query DSL — or the
ES|QL statement the fragment carries — into a `pyarrow` `ArrowStream`. `explain()` reports the index
set with `pruning_proof=unknown` (Elasticsearch has no EXPLAIN), `mine_queries`/`mutability_stats`
raise `NotSupported` naming their capability, and `cancel()` is idempotent.

Index selection happens before any request: a `range` on the family's time field is turned into the
exact monthly indices to touch, an unbounded read over a family bigger than `Limits.max_partitions`
is refused with `PARTITION_SCAN_ALL` (fix names the field), and a window covering too many months is
refused with `COST_TOO_HIGH`. Row and byte caps are enforced in the adapter and reported on the
stream (`total_hits`, `dropped_rows`, `dropped_values`, `touched_indices`, `took_ms`).

## Decisions

* **The alias is the table.** It is the name that survives monthly rotation; a query against one
  month's index silently loses next month's rows. An index that belongs to no alias becomes its own
  table so nothing is invisible. `TableKind.INDEX` with the member list in `comment`.
* **The time field is configuration, not a guess.** `options["time_field"]` drives (a) the partition
  key, (b) index narrowing, (c) which range clause prunes. Without it, a family whose mapping has
  exactly one `date` field infers that one; a family with two date fields (`start_time`,
  `insertion_time`) is never guessed at, because narrowing on the wrong date field drops documents.
* **ES|QL is selected by the fragment, not by a translator.** The fragment's `dsl.esql` is sent to
  `_query` when the probe found it; otherwise the same fragment's `query` goes to `_search`. This
  adapter does not translate DSL to ES|QL — that is the compiler's job (C lane) — so there is no
  half-working translator here.
* **One `POST` is allowed, and only the server forced it.** `GET /_query` returns 405 with
  `allowed: [POST]` on 8.15.3, so `SearchOnlyTransport` allows `GET` plus `POST /_query` and nothing
  else; the test asserts the 405 so the exception can never grow silently. `_search` is sent as
  `GET` with a body, so no other write-shaped method exists in the code path.
* **Aggregation bodies are refused**, not approximated: `dsl.aggs` is not a key this adapter accepts
  (`INVALID_SPEC` naming the field). Aggregating after the fetch is the federated engine's job, and
  half-implemented bucket-to-row conversion would be worse than saying no. `probe()` still reports
  whether the cluster answers aggregations (`features.aggregations`).
* **`explain_plan` is reported supported**, with a detail that says Elasticsearch has no EXPLAIN and
  that `explain()` returns the index set with `pruning_proof=unknown`. That keeps `supports()` ==
  "the method answers", which is what the conformance kit checks, while the proof itself stays
  unknown so the planner caps by statistics.
* **`track_total_hits: true`** in every search: reporting a truncated result without the real total
  would make a row cap look like a complete answer.
* **`from` is always 0.** `Limits.max_rows` bounds the answer; deeper paging is the governor's and
  the cache's business, and Elasticsearch refuses `from+size > 10_000` anyway.

## Deviations

* `pyproject.toml`: one line added to `[project.entry-points."mdqm.adapters"]`
  (`elastic = "mdqm.adapters.elastic:ElasticAdapter"`). Without it a deployment config
  `adapter: elastic` fails with `AdapterNotRegistered`; the file is not in the task's `owns` list.
* `tests/unit/test_es_adapter.py` is a second test file (the task named only the integration one):
  the index-name arithmetic, query-tree time bounds, value conversion, catalog assembly and the
  transport refusal run without Docker, which is what `scripts/check.py` needs.
* Nothing else; no change to `TASKS.md`, `tasks.json`, `docs/DESIGN.md` or another lane's code.
  DESIGN already describes this shape ("Elasticsearch = the list of selected indices (no EXPLAIN)",
  "Query DSL always available, ES|QL or SQL API when the probe finds them"), so no design text
  changed.

## Dependencies

None. `httpx`, `pyarrow` and `pydantic` were already dependencies; the `elasticsearch` Python
package is deliberately not used (its client/server version coupling is exactly what a generic
adapter must not inherit).

## Plan issues

* The task text says "ES|QL used when available, DSL otherwise" without saying who produces the
  ES|QL. I chose "the fragment carries it" because an adapter that translates DSL to ES|QL is a
  compiler. If the C lane wants the adapter to translate instead, the fragment contract has to
  change — worth settling before a second ES consumer exists.
* `esql_support` is a constructor flag used to stub the probe in tests. A real operator whose proxy
  blocks `/_query` can use it too, but no config key exposes it yet.
* `OPTIONAL_METHODS` has no name for "aggregations pushdown" or "ES|QL", so the probe records those
  two facts in `EsFeatures` (exposed as `adapter.features()`) rather than in `Capabilities`. If a
  feature is ever gated on them, they belong in the capability table, not in an adapter-only object.
* The integration fixture loads the small world itself because the cluster arrived empty (and was
  emptied again mid-session by another run of the D07 seed test, which deletes its indices on
  teardown). Two lanes running `test_seed_es.py` and `test_es_adapter.py` at the same time will
  fight over the alias; a shared session-scoped fixture would be the honest fix.
