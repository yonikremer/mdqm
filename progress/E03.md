## Summary
`tests/integration/test_acceptance_e2e.py` drives the **real MCP client** (`scripts/mdqm_call.py`, real
streamable HTTP, bearer auth) against the **running server container**, which talks to real PostgreSQL.
Nothing is imported from the tool modules: if the transport, the auth, the tool envelope or the pipeline
break, these fail.

Five acceptance claims, one test each:
1. **the cross-source answer** -- `avg_limit_by_status_billing` through the tools equals E01's ground
   truth to 1e-9;
2. **the cache** -- a repeated identical question over a cacheable table (`events_count_window`,
   `billing.usage_events` is `append_rarely`) reports `cache_hit: true` with a per-source `fetched_at`;
3. **the partition refusal** -- a `usage_events` question with no time bound is refused with
   `PARTITION_SCAN_ALL` and a `fix`;
4. **the write surface** -- a DELETE cannot even be *expressed*: `query` has no raw-SQL field, the SDK
   rejects `spec.raw` as `extra_forbidden`, and `pg_stat_statements` holds zero write statements;
5. **the context pack** -- `find_data` returns items inside its token budget with rendered text.

## Two real defects found and fixed while proving this
1. **`explain()` dropped the fragment's bound parameters.** Any parameterised fragment died with
   `query has N placeholders but 0 parameters`, which surfaced to the agent as
   `INTERNAL_ERROR ... report correlation id ...`. A cross-source question therefore failed before it
   ever ran. Fixed in `src/mdqm/adapters/postgresql.py`; the cross-source acceptance test now passes.
2. **The cache claim is table-scoped, and the layer must say so.** Only `append_only`/`append_rarely`
   tables are cacheable (`CACHEABLE_MUTABILITY`), and `billing.accounts` declares no mutability, so it
   is deliberately not cached. The test now uses a cacheable table and the reason is written in it --
   the first version asserted a claim the product never made.

## Decisions
- The deletion claim is proven at the surface, not by watching a refusal message: a tool that cannot
  express a write is stronger than one that refuses it, and `pg_stat_statements` proves nothing ran.
- The client is the operator CLI rather than an in-process SDK client: it exercises the same path a
  hook or an agent uses, and it does not couple the test to event-loop details.

## Not verified

- Only PostgreSQL is exercised end to end; Oracle/SQL Server/Elasticsearch have their own adapter and
