## Summary

`src/mdqm/review/digest.py` renders the weekly human-in-the-loop digest and delivers it. It reads
pending proposals from the S12 review queue, picks at most ten, and renders each as one short
localised question with its evidence, confidence and a short id, offering `yes / no / other`
(`כן / לא / אחר`). Output is a plain-text body, an HTML page (Hebrew is `lang="he" dir="rtl"`,
English `lang="en" dir="ltr"`) and, when SMTP is explicitly configured, an `EmailMessage` with both
bodies sent through `smtplib`. The page is always written; email is the extra. `record_answer` maps a
reply back through `ReviewQueue.approve` / `.reject`, so `curated/*.yaml` is still written by the
queue alone.

## Decisions

- **Impact ranking = `(-confidence, id)`.** Mining stores usage counts, but a proposal row carries no
  fingerprint to join them on, so confidence (with the id as a deterministic tie-break) is the only
  honest "impact" available tonight. The sort is redone inside the digest rather than trusted from
  `queue.pending()`, so a queue change cannot silently make the digest non-deterministic.
- **`other` decides nothing.** `record_answer(..., OTHER)` returns `recorded=False` and leaves the
  proposal `pending`: an open reply is not yes/no, and guessing which decision was meant would put a
  machine guess into `curated/`. Yes/no go through the queue (approve/reject), never the files.
- **Email needs an explicit configuration, and the fallback is silent-but-logged.** No `smtp.host`,
  no address, an address that contains a newline, or any exception from connect/STARTTLS/login/send
  all produce `channel=page`, the page already on disk, the reason in `DigestDelivery.reason` and one
  log line. Nothing is raised, so a nightly run cannot die on a mail server.
- **STARTTLS verifies the certificate** (`ssl.create_default_context()`). A relay this host does not
  trust degrades to the page: the digest is not secret, the SMTP credentials are.
- **The password is read from `SmtpSettings.password` (a `SecretStr`, env/init only; the YAML loader
  already refuses a literal `password` key).** It is unpacked only at `login`, and scrubbed from any
  exception text that reaches the log or the delivery reason.
- **The default recipient is `smtp.sender`** when the caller names none: `SmtpSettings` has no
  recipient field and I did not add one (see Deviations).
- **Page location** defaults to `<paths.cache_dir>/digest/digest-<lang>-<year>-W<week>.html`, one file
  per language and ISO week, so a re-render overwrites instead of piling up.
- **Digest id** is the SHA-256 of (language, proposal ids): the same queue renders the same id, a new
  pending proposal changes it.
- Hebrew pages are entirely Hebrew rather than Hebrew strings in an English shell, because a
  mixed-direction page puts punctuation on the wrong side.

## Deviations

- The task says "email via smtplib (host/port/TLS from Settings)"; I used `SmtpSettings` for
  host/port/sender/username/password/starttls (all existing, uncapped) and a bounded 30 s socket
  timeout. No settings change was needed, so `src/mdqm/config/settings.py` is untouched.
- The task names no recipient source; I take an optional `recipients` argument and fall back to
  `smtp.sender`. A dedicated `smtp.recipients` field would be nicer, but that file is another lane's.
- I did not register the digest as a scheduled pipeline stage (S01) or expose it as a CLI command:
  `mdqm/pipeline/**` and `mdqm/cli.py` are outside this task's `owns` list. The module is callable and
  tested; wiring it into a scheduler is a follow-up task, not a silent gap.
- Golden files live in `tests/data/golden/` (the `golden` fixture in `tests/conftest.py`), not under
  `src`, because that is where this repo keeps goldens.

## Dependencies

none (stdlib `smtplib`, `ssl`, `email`, `hashlib`, `html`, plus existing `pydantic`).

## Not verified

- **Never sent through a real SMTP server.** No SMTP server exists here and `tests/unit` blocks
  sockets, so the transport is injected and the tests assert on the `EmailMessage` that would be sent,
  the STARTTLS call and the login arguments. A real relay, a real TLS handshake and a real
  RFC 2047 Hebrew subject header are unverified end to end.
- Real Hebrew mail-client rendering (RTL alignment, subject folding in Outlook vs a web client) was
  not observed; only the markup and the encoded message were checked.
- No acceptance item was left unverified.

## Plan issues

- `TASKS.md` S13 says "impact (usage score from mining)", but S08's mined scores are keyed by query
  fingerprint and `review_proposals` has no column linking a proposal to a fingerprint. Either S09/S12
  gains an `impact` column (filled at submit time) or the task text should say "confidence".
- `SmtpSettings` has no recipient address field, so every caller must supply recipients. A
  `smtp.recipients: list[str]` default would make the digest self-contained for a scheduler.
- The digest reads pending proposals only; a proposal that was `never_ask`ed is correctly never
  asked, but there is no "ask at most once per week" suppression, so a proposal the human skips
  reappears next week. That is probably right, but it is a policy nobody has written down.
