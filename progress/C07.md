## Summary

`src/mdqm/planner/time.py` is the pure time planner: it turns a spec `time` intent plus a table's
`time_columns` metadata into sqlglot predicates, notes and (on refusal) an agent-facing error.

- `events_in_range` filters the column marked `use_by_default` (event time, indexed) over a
  half-open `[start, end)` window resolved from `last` or `from`/`to`. No ingestion predicate is
  invented for a period question.
- `new_since X` emits `insertion_time >= X` **and** the derived bound `start_time >= X - max_lag`.
  The original predicate stays, so late rows are still returned; the derived one only narrows the
  scan and the partitions.
- Unknown lag, or a lag whose nightly verification failed (`lag_unverified`), refuses to derive and
  returns `INSERTION_TIME_NO_BOUND` whose `fix` names the spec's `time` field.
- A window whose end falls inside the last `max_lag` gets the `partial_data_possible` note.
- `known_as_of(table, as_of, start, end, ...)` answers "what did we know at T": event range plus
  `insertion_time <= T`.
- When the partition key **is** the ingestion column, an event range `[X, Y)` also yields the
  widened ingestion range `[X + min_lag, Y + max_lag)` (event time is still filtered too).

The never-loses-rows invariant is proved with hypothesis over the D02 world executed in DuckDB,
not with a handful of hand-picked cases.

## Decisions

- **`predicates` are sqlglot `exp.Expression` values**, not SQL text, so the compiler can AND them
  into the fragment AST and the guard can inspect the result. `TimePlan.where_sql(dialect)` renders
  them for tests and diagnostics.
- **`lag_unverified: frozenset[str]`** is the input that represents "the nightly check found a
  violation": naming an ingestion column there disables derivation for that column. The semantic
  model has no runtime field for verification state, and the planner must stay pure, so the caller
  injects it instead of the planner reading the store.
- **`min_lag` is used only for the partition-key-is-ingestion widening** (`X + min_lag`). For the
  derived bound on the event column only `max_lag` matters: `start_time >= since - max_lag` is the
  weakest true bound, which is the safe direction.
- **`_resolve_window` returns `None` for an under-specified or empty window** and the caller raises
  `INVALID_SPEC` naming `time`, rather than guessing a default window. Conservative: a guessed
  window would silently answer a different question.
- **Naive `exec_ts` / `since` / `from` / `to` raise `ValueError`** (a programming bug), not an
  `ErrorResponse`: an agent can never send these, only internal callers can.
- **`partial_data_possible` is emitted for `new_since` when `since > exec_ts - max_lag`** and for
  `events_in_range` when the window end is later than `exec_ts - max_lag`. In both cases rows for
  the tail may not have been inserted yet, which is exactly what the note warns about.
