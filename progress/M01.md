## Summary          Built the MCP server skeleton in `src/mdqm/server/`: `create_server()` returns an
                     `MCPServer` (MCP SDK 2.3.0) exposing exactly five coarse tools -- `find_data`,
                     `query` (typed to the existing `mdqm.spec.QuerySpec`), `get_more`, `history`,
                     `feedback` -- each with pydantic input and output schemas and a short
                     weak-model description (what, when, one example). Bodies are honest typed stubs
                     returning `status: "not_implemented"` plus `problem`/`fix`; no query is faked.
                     `GET /healthz` (public) and `POST /context` (stub, bearer-checked) are custom
                     routes. Auth is a pluggable `TokenVerifier` protocol (the SDK's shape, so it is
                     passed straight to `MCPServer(token_verifier=...)`) with `StaticTokenVerifier`
                     reading a JSON token file and mapping each token to a `UserIdentity`; identity
                     reaches handlers as a token-free `RequestContext`. `mdqm serve --host --port`
                     runs it over streamable HTTP. `scripts/gen_tool_schemas.py` writes
                     `docs/tool-schemas.json`, and a test fails if the file goes stale.
## Decisions        - MCP 2.x API verified against the installed wheel (mcp 2.3.0), not memory:
                     `from mcp.server.mcpserver import MCPServer`; `MCPServer(name=, version=,
                     instructions=, token_verifier=, auth=AuthSettings(...))`;
                     `server.add_tool(fn)` (name = `__name__`, description = docstring, outputSchema
                     auto-derived from the return annotation); `@server.custom_route(path, methods=)`
                     with a Starlette `Request -> Response` handler; `server.streamable_http_app()`;
                     `server.run("streamable-http", host=, port=)`;
                     `mcp.server.auth.provider.AccessToken`/`TokenVerifier`;
                     `mcp.server.auth.middleware.auth_context.get_access_token()` (populated inside a
                     tool handler over stateful streamable HTTP -- confirmed by an end-to-end spike
                     before writing the design, because it was the one unproven assumption).
                   - Identity lives in the SDK `AccessToken`: `subject` = user id,
                     `claims["display_name"]` = human name, `client_id` = `mdqm:<user_id>` so the SDK's
                     session-ownership check stops one user from reusing another user's session.
                   - Token comparison is by sha256 digest of the presented token, so the lookup never
                     compares secret bytes and a rejected token is never echoed. No token value ever
                     appears in a log line, an error message or a tool result; `RequestContext` holds
                     no token at all.
                   - Dev token file is JSON (`{"tokens": [...]}`), path from `MDQM_TOKENS_FILE`, else
                     `tokens.json` in the cwd. It is a mount/env-pointed deployment secret, never a
                     repository file. YAML was rejected on purpose: AGENTS §11 says secrets never live
                     in YAML, and this is the one place a token value legitimately sits.
                   - `NotImplementedResult` carries `user_id`: it makes the auth wiring observable to a
                     caller (a misissued token shows up in the first call instead of an empty answer).
                     When the pipeline lands the id moves into history/audit records.
                   - `validate_token_resource=False` on `AuthSettings`: tokens are opaque personal
                     tokens, not RFC 8707 resource-bound grants, so binding them to a URL would break
                     every dev token and warn on every startup.
                   - `create_server()` takes no `Settings` and does no I/O, so the schema export, the
                     tests and `serve()` all build the same object from an injected verifier.
                     `serve()` loads the verifier from the env-pointed file and refuses to start
                     without one: an unauthenticated server is never an option here.
